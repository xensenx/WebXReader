Storage & Persistence

WebXReader keeps everything on the client: book data, reading positions, highlights and per-book preferences live in a single IndexedDB database named webxreader, while global preferences live in localStorage. All access goes through one module — src/core/storage/database.ts — which exposes a typed, async API that hooks consume. This page documents the schema, every exported function, and the transactional and quota behaviors you need to know before touching storage code.

The layout at a glance

Two storage mechanisms divide the responsibilities:

  • IndexedDB database webxreader (version 1) — eight object stores holding everything per-book plus a legacy settings store. Big binary payloads (EPUB/PDF/CBZ buffers) are kept in their own store so library listings never touch them.
  • localStorage key webxreader.preferences.v1 — the serialized global UserSettings record. Faster to read synchronously at startup, and quarantine-able from "clear library" operations.
// Mental model — real definitions live in database.ts
DB_NAME = 'webxreader'
DB_VERSION = 1
SETTINGS_STORAGE_KEY = 'webxreader.preferences.v1'  // localStorage

stores: {
  books, bookContent, progress, bookmarks, annotations,
  settings,        // legacy fallback for settings only
  bookSettings, covers,
}

Opening the database

The module caches a single connection: the first call to the internal getDb() opens the database and stores the instance; on close the cache is invalidated so the next call reopens. onversionchange closes the connection when another tab requests an upgrade, and onblocked logs a warning while waiting for older connections. Two generic helpers do the drudgery: withTransaction(store, mode, operation) for single-store work, and getAllFromStore(store, index?, query?) for listing.

THE MOST COMMON ABORT CAUSE

QuotaExceededError-class aborts are the dominant real-world transaction failure for a browser-based library: a large originalFile arriving when the quota is nearly spent aborts the whole saveBookBundle, which is by design — the library surface stays consistent and the import dialog reports a save failure instead of a half-written book. Pair this reading with the persistence guidance in Persistence & quota.

ADDING A STORE OR INDEX

Any schema change must bump DB_VERSION and add a guarded migration under the existing if (oldVersion < 1) block (e.g. a following if (oldVersion < 2)). Creating stores unconditionally would throw for existing databases where they already exist.

Atomic transactions

Whenever more than one store must change together, the code opens a multi-store transaction and relies on IndexedDB's atomicity: if any request errors or the transaction aborts, every write in the transaction is rolled back. The three critical ones:

  1. saveBookBundle — importwrites [books, bookContent], or [books, bookContent, covers] when a cover was parsed. Uses add for book and content, and put for the cover. On abort the promise rejects with "Book import was rolled back: …" — a failure here leaves no half-imported book behind.
  2. updateBookAndCover — save from the library editorwrites [books, covers]; cover present → put, cover absent → delete. This pairing is exactly what makes removing a cover a durable, all-or-nothing change.
  3. deleteBook — cascading removaltouches [books, bookContent, progress, bookmarks, annotations, bookSettings, covers]: direct deletes for the five key-matched stores, plus an openCursor(IDBKeyRange.only(id)) walk over the bookId index of bookmarks and annotations, deleting each match. No orphaned highlights survive.

The bundle transaction looks like this (simplified from the source):

const storeNames: StoreName[] = coverData
  ? [STORES.books, STORES.bookContent, STORES.covers]
  : [STORES.books, STORES.bookContent];

const tx = db.transaction(storeNames, 'readwrite');
tx.objectStore(STORES.books).add(book);
tx.objectStore(STORES.bookContent).add(content);
if (coverData) {
  tx.objectStore(STORES.covers).put({ bookId: book.id, data: coverData });
}
tx.oncomplete = () => resolve();
tx.onabort   = () => reject(new Error(`Book import was rolled back: ${tx.error?.message ?? 'transaction aborted'}`));

Settings storage strategy

Global preferences are dual-powered deliberately — synchronous startup reads and resilience when localStorage is unavailable:

  1. Read pathgetSettings() parses webxreader.preferences.v1 from localStorage and normalizes it over DEFAULT_SETTINGS (so new fields backfill automatically). If the key is absent it goes to the legacy store.
  2. Legacy migrationif the IndexedDB settings store has a global record, it is re-checked against localStorage once more (a preference written while the async read was pending wins), normalized, written to localStorage, and the legacy record is deleted. If the localStorage write fails mid-migration the legacy record is kept, so nothing is lost — the migration just retries on the next read.
  3. Write pathsaveSettings() tries localStorage first; the IndexedDB store is only a fallback when the setItem throws (quota errors, cookie-blocked contexts).
SETTINGS NEVER JOIN BACKUPS FROM LOCALSTORAGE DESIGN

Backups do include settings — exportBackup() reads the merged getSettings() result and restoreBackup() applies the backup's settings via saveSettings() after the main transaction commits. The legacy settings store itself is never exported.

Per-book settings (BookSettings) are plain IndexedDB records — always written with saveBookSettings(). The merge happens at read time in useReaderSettings(bookId): per-book values win field-by-field, while wordSpacing and theme always come from the global record (field semantics). The settings UI and the persisted theme attribute (data-theme on <html>) are wired through useSettings plus a SettingsProvider context; useSettingsContext() throws if used outside the provider.

How progress saves actually behave

The storage layer is passive; the cadence lives in src/hooks/useReadingProgress.ts, and knowing it explains most data-timing surprises:

  • Every progress update persists through a 2-second debounce — rapid scroll bursts coalesce into one put into progress.
  • The hook exposes flush(), which is called on unmount and on navigation so the last position is not lost.
  • Each save re-evaluates the book: overallProgress ≥ 0.98 → 'completed', > 0 → 'reading'.
  • The Book record is only rewritten when the status actually changed or more than 30 seconds passed since the stored lastOpenedAt — cheap in steady state.

Inside exportBackup()

The export gathers its inputs in two layers — settings through getSettings(), and a single readonly transaction over the other six stores. Every store read is issued simultaneously via getAll(); a completion counter resolves the promise only when all reads finished, and any single read failure rejects the whole export:

const [db, settings] = await Promise.all([getDb(), getSettings()]);

const tx = db.transaction(
  [STORES.books, STORES.bookContent, STORES.progress, STORES.bookmarks,
   STORES.annotations, STORES.bookSettings],
  'readonly'
);

const results: Partial<BackupData> = {
  version: 2,
  exportedAt: Date.now(),
  appVersion: '1.0.0',   // hardcoded — see Import & Backup → backup format
  settings,
};

// five stores (books, progress, bookmarks, annotations, bookSettings)
// map verbatim onto same-named array keys in the backup ...

// ... bookContent is the only transformed store:
const contentReq = tx.objectStore(STORES.bookContent).getAll();
contentReq.onsuccess = () => {
  results.contents = contentReq.result.map(serializeBookContent);  // buffers → base64
};

serializeBookContent keeps bookId, format, rawText and chapters as-is and converts a present originalFile ArrayBuffer into originalFileBase64 with the chunked base64 helpers. Note what export does not read: the covers store (covers do not travel), and the legacy settings store (the preference material has already been merged into the getSettings() result).

The restore path, step by step

restoreBackup(backup) is the most defensive function in the module. In order:

  1. Validate the envelopeisBackupObject() accepts version 1 or 2, requires numeric exportedAt and the book/progress/bookmark/annotation/bookSettings arrays, and allows contents to be absent (v1). Anything else throws "Invalid or unsupported backup format".
  2. Dedup booksisBookRecord() requires id, title, contentHash and sourceFormat; candidates are then skipped when their id exists in the library or their contentHash matches a book already present. Each skip appends a human-readable string to the returned errors array — skips are not failures.
  3. Decode & sanitize contentonly contents records belonging to a restorable id are used. Base64 binary payloads are decoded chunk-safely (atob plus an explicit byte copy into a fresh ArrayBuffer), and every restored chapter body passes through sanitization — see the security callout below. Chapter trees are validated recursively with depth capped at 100.
  4. Write atomicallyone readwrite transaction over [books, bookContent, progress, bookmarks, annotations, bookSettings]. Children records only restore for book ids that survived dedup, so no orphaned highlights are imported. Any error aborts the whole restore.
  5. Restore settings lastafter the transaction commits, the backup's global settings go through saveSettings(); only then does the promise resolve with { booksRestored, errors }.

Two validation helpers deserve explicit mention when you extend the format: isBackupChapter verifies a chapter recursively (id/title strings, finite level/order, recursive children) and refuses trees deeper than 100 levels; isBackupBookContent requires a non-empty string bookId and a known BookFormat value. An invalid book record is merely skipped with an error string, but an invalid content payload throws — a broken contents entry fails the entire restore.

RESTORE-TIME SANITIZATION IS THE SECURITY BOUNDARY

sanitizeRestoredChapter() runs sanitizeReaderHtml() over every chapter body on restore — even though the backup is your own export — because a hand-edited or exchanged backup file is attacker-controllable input like anything else. Never bypass this when adding new content-bearing fields; the dedicated XSS regression test suite in Testing & Quality covers it.

Persistence & quota

Three maintenance functions round out the story — and they matter because an unhappy browser can delete your library without asking:

  • getStorageEstimate() surfaces { usage, quota } in bytes from navigator.storage.estimate(); the settings screen shows this breakdown. Returns null where the API is unavailable.
  • requestPersistentStorage() calls navigator.storage.persist() and returns whether the browser granted it. Persistent storage removes the eviction pressure described below (browsers may still refuse, typically based on engagement heuristics).
  • Without persistence, idle-timer eviction of best-effort storage applies: browsers may purge IndexedDB data for sites that have gone unused for a while, especially under disk pressure.
YOUR LIBRARY IS EVICTABLE

Clearing site data, using a private window, or quota eviction removes book content permanently — WebXReader has no server copy to fall back on. Ask for persistent storage, and keep a routine JSON backup for anything you care about. As advice: comfortably-sized text formats restore fastest; full-binary v2 backups of many large EPUBs make both the export download and the restore noticeably heavier.

Clearing data

clearDatabase() opens one readwrite transaction over the seven library stores — books, bookContent, progress, bookmarks, annotations, bookSettings, covers (filtered to those actually present) — and clear()s each:

SETTINGS ARE PRESERVED

The settings store is intentionally excluded — indeed, clearing it would defeat the localStorage preference strategy. "Clear all data" removes your library and reading state but keeps general site preferences (theme, typography defaults, import warning threshold). The settings screen separates the two concerns: it wires clearDatabase() for data, and a separate reset-preferences action with a confirmation dialog for clearSettings().

HOOKS CONSUME ALL OF THIS

App code never touches database.ts storage functions directly except through src/hooks/: useBooks (module-level books cache with invalidateBooksCache()), useReadingProgress, useBookmarks, useSettings and useReaderSettings. Keep it that way when adding features — the cache invalidation and debounce timing live in exactly one place this way. See Reader and Library for the consumption side.

The base64 encoding helpers

Two local functions bridge JSON-friendly strings and binary ArrayBuffers. Both process data in 0x8000-byte (32 KiB) chunks — String.fromCharCode(...spread) on one huge array risks blowing the call stack, so the spread is fed subarray-by-subarray

function toBase64(data: ArrayBuffer): string {
  const bytes = new Uint8Array(data);
  let binary = '';
  const chunkSize = 0x8000;
  for (let offset = 0; offset < bytes.length; offset += chunkSize) {
    binary += String.fromCharCode(...bytes.subarray(offset, offset + chunkSize));
  }
  return btoa(binary);
}

function fromBase64(value: string): ArrayBuffer {
  const binary = atob(value);
  const bytes = new Uint8Array(binary.length);
  for (let index = 0; index < binary.length; index++) bytes[index] = binary.charCodeAt(index);
  return bytes.buffer;
}

The decode side copies byte-by-byte into a new buffer rather than slicing the binary string's internal representation — the resulting ArrayBuffer is a clean, transferable payload suitable for the BookContent.originalFile slot.

What happens if two tabs write simultaneously?

IndexedDB serializes at the transaction level, so the last committed write wins per record, but no record is corrupted halfway. Two things to know: onversionchange closes the cached connection in tabs that lose an upgrade race, and a pending version upgrade fires the onblocked warning until the older connections close. Reader-created data (progress, annotations) is written from whichever tab is actually reading that book, so conflicting edits on the same book across two open tabs are the only realistic conflict case — and they resolve to last-write-wins with no merge.
