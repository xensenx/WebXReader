Library & Metadata

The library is the app's home screen and its most stateful view. This chapter walks through LibraryView composition, the view-state persistence layer, the custom drag-and-drop ordering algorithm, bulk operations, the details dialog with its cover editor, and the import dialog queue — everything between "books in IndexedDB" and "books on screen".

Composition map

src/components/library/LibraryView.tsx is the orchestrator (~1,080 lines) and owns nearly all view state. It composes these children:

Component (src/components/library/)Role
LibraryToolbar.tsxSearch box, filter chips, sort selector, layout toggle, selection entry points, import button.
BookCard.tsxGrid item: cover image (or fallback with the title's initial + format label), progress bar, selection semantics, keyboard activation, drag pointer handling. Has its own onKeyDown handler.
BookList.tsxList rows for the list layout: compact row with title/author/progress; also has an onKeyDown activation handler.
ImportDialog.tsxMulti-file import queue with per-file status (see below).
BookDetailsDialog.tsxMetadata editing, tags, rating, favorite/archive/status, cover editor (see below).

Data comes from one hook: useBooks(), which returns { books: LibraryBook[], loading, error, refreshBooks, removeBook, removeBooks, toggleFavorite, updateReadingStatus, toggleArchive }. LibraryBook = Book & { readingProgress } with the progress derived from the progress store — never persisted as part of the book record (see Architecture for the caching details).

ACTIVATION PATTERN

Fact: accessible button/card activation is implemented directly in LibraryView.tsx, with matching onKeyDown handlers in BookCard.tsx and BookList.tsx — cards are real focusable elements (tabIndex 0) that act on Enter and Space, and double as role="checkbox" with aria-checked during selection mode. Advice: copy this pattern (role swap + key handling on the container, guarded by e.target !== e.currentTarget) for new selectable library artifacts instead of layering a nested button.

View state: search, filter, sort, layout

The library remembers itself across navigation using src/features/library/library-state.ts, which exports getLibraryViewState, saveLibraryViewState, updateLibraryScroll, and clearLibraryViewState. State lives in sessionStorage under the key webxreader_library_view_state, mirrored in a module-level in-memory copy for synchronous reads during component lifecycles.

WHY SESSIONSTORAGE AND NOT THEME-LIKE PERSISTENCE

View state is contextual: it should die with the tab. Sorting, layout and book order are preferences: they belong in the settings document so they survive restarts. Keep new library state on the correct side of that line.

Lifecycle

Conceptual flow on each mount:

  1. MountLibraryView reads the persisted view state synchronously (memory first, sessionStorage fallback) to seed search query and filter.
  2. Hydrate booksuseBooks() loads listBooks() and listProgress() in parallel, derives readingProgress per book (forced to 1 for completed status), and re-reads covers from the covers store when coverImage is not a data:/blob: URL.
  3. Hydrate settingsLayout, sort field/direction, and customBookOrder arrive via SettingsContext; a useEffect copies new customBookOrder values into local state when they exist.
  4. Apply ordering pipelinefilter → search → sort → custom-order overlay produce the rendered list.
  5. User interactionsorts/filters write back to UserSettings, scrolls update the session state, and the cycle continues without remounting.

Sorting and the custom order field

Sort configuration is a pair of UserSettings fields:

SettingValuesDefault
librarySortField'custom' | 'title' | 'author' | 'importedAt' | 'lastOpenedAt' | 'progress''importedAt'
librarySortDirection'asc' | 'desc''desc'
customBookOrderstring[] of book ids[]

library-custom-order.test.ts (Testing & Quality) locks this behavior. The key rule: when librarySortField !== 'custom', the order array is ignored entirely, so a one-time drag does not get reverted by a later re-sort — both simply stop interacting. Dragging a card automatically switches the sort field to 'custom': updateSettings({ librarySortField: 'custom', customBookOrder: finalOrder }) happens at drop time.

Custom drag-and-drop ordering, conceptually

LibraryView implements ordering without any drag-and-drop library. The mechanism has three cooperating parts:

  1. Pointer captureonPointerDown on a card calls e.currentTarget.setPointerCapture(e.pointerId), so the entire gesture — including pointers that leave the card — keeps delivering events to the dragged element. No global mousemove listeners on window, no event leakage between simultaneous gestures.
  2. FLIP hit-testingThe current visual positions of the cards are captured before the drag perturbs layout (the code comments call this out at the top of the interaction block). Cards' layout slots move immediately while a FLIP transform visually translates each card from its old position; hit-testing against the captured rectangles decides which neighbor a dragged card previews as its target slot.
  3. Persist on dropThe final order is written via updateSettings({ librarySortField: 'custom', customBookOrder: finalOrder }), then the local copy is explicitly reset from settings.customBookOrder ?? [] so the persisted source of truth and the visual order are re-anchored in the same tick. Recent commits (fix(library): stabilize drag reorder previews) hardened this area — it is deliberately subtle.
ADVICE: EXTENDING THE ORDERING

Because both layouts consume the same ordered id list, the mechanism works with the grid and the list alike — keep any new layout reading the same effective-order helper instead of re-sorting locally. If you touch the FLIP code, run vitest run src/test/library-custom-order.test.ts and test with a real pointer drag, since the unit tests cover the ordering function, not the gesture.

Bulk selection

Selection state is a Set<string> of book ids in LibraryView. While active, cards switch to role="checkbox" semantics; a bulk action bar renders with a count line ("N book selected / books selected") and the following operations:

Bulk actionImplementation
DeleteOpens a ConfirmDialog ("Delete N book(s)?") warning that all reading progress, bookmarks and annotations are removed from the device; then removeBooks(ids), deleting one by one with a final refresh.
FavoriteToggles favorite across all currently selected books (looped updates through updateBook).
Archive / UnarchiveLabel flips based on whether every selected book is already archived.
Status: mark reading / mark unreadDisabled unless at least one selected book isn't already in the target state.
Clear selectionNegative-state ghost button.

Buttons use availability derived from the selected set (e.g. "Unarchive" vs "Archive" based on selectedBooks.every(book => book.archived)) rather than relying on the user to interpret disabled state. Failures alert with the underlying error message.

Anatomy of a book card / list row

  • Cover: <img loading="lazy" draggable={false}> when coverImage exists, otherwise a fallback tile with the uppercased initial of book.title and the sourceFormat label.
  • Reading progress: computed as a rounded percentage. The rule in BookCard: trivially 100 for 'completed', 0 for 'unread', otherwise the derived readingProgress clamped to 0–1 and multiplied by 100. Cards render a thin progress bar beneath the cover.
  • Selection state: a selected modifier class and the aria-checked wiring described above; dragging adds a cardDragging class and the dragged cover is marked data-drag-preview for the FLIP system.
  • Keyboard: Enter/Space activate the card (open details or enter selection depending on current mode) — Esc exits selection when handled by the container (LibraryView's own onKeyDown).

Cover editor

All validation and resizing happens in src/utils/cover-image.ts. Constants are fixed:

ConstantEffect
MAX_COVER_FILE_SIZE = 20 MBFiles above it are rejected with "Choose an image smaller than 20 MB." (URL downloads check content-length too).
MAX_COVER_EDGE = 1200 pxOutput images are downscaled so the longest edge is ≤ 1200 px.
MAX_COVER_PIXELS = 40,000,000Giant-but-legal-dimension images (decompression bombs) fail dimension validation before a canvas is touched.
Encoders usedcanvas.toDataURL('image/webp', 0.86) — WebP at quality 0.86 is the persisted format.

Both entry paths are exported:

  • prepareCoverFile(file) rejects non-image/* files, then decodes via createImageBitmap when available (falling back to an <img> + object URL), resizes, and returns a WebP data URL.
  • importCoverFromUrl(url) accepts only http: or https: URLs and refuses credentials embedded in the URL (it also drops credentials: 'omit' on the fetch). The result is a CoverImageResult { data, width, height, isRemote }.
CORS FAILURE FALLBACK (THE URL IMPORT STORY)

Many hosts serve <img> display happily but block cross-origin downloads. When the fetch throws, the editor does not abort: it loads the URL in an <img> just to read naturalWidth/naturalHeight, then keeps the validated URL as-is with isRemote: true. Consequences: the cover renders, costs no local storage, but requires network (and its availability) forever after — unlike local covers, which are WebP data URLs in the covers store (Storage & Persistence). The input only helps if it is a direct image link; HTML pages are rejected by content-type.

Saving the cover calls the storage pair saveCover / updateBookAndCover so the cover blob and the book's reference update atomically. The dialog also tracks originalCoverImage: the first cover ever captured at import is preserved on the book (Book.originalCoverImage) and powers the Reset to original action. The reset affordance appears only when the current cover differs from the original (canResetCover = coverImage !== (originalCoverImage || '')), and offers "Reset to default" when the book never had a cover at all.

Import dialog

ImportDialog manages a multi-file queue and is the only importer UI — parsing itself is delegated to importFile from src/features/import/import-service.ts (documented step by step in Import & Backup). Behaviors:

  • Size warning: the threshold is settings.importSizeWarningMB × 1024 × 1024. Files over it show Large file (X MB). Processing locally; this may take a moment… and continue rather than blocking. The setting itself defaults to 50 and is clamped to 1..5000 in SettingsView (use clamp(n, 1, 5000) semantics when writing to it).
  • Queue + statuses: each file gets a status line rendered as Imported, Skipped duplicate (when dedup hit an existing contentHash), or Failed, driven by the import-service result (result.isDuplicate plus the thrown error text). Duplicates surface the existing book id/metadata so you can jump to it instead of blind re-import.
  • autoDetectChapters: checkbox mirrors the app-level UserSettings.autoDetectChapters setting and is passed into the import call; parsing honors it by splitting TXT/MD/HTML on heading patterns (Formats & Parsers).
ADVICE: TESTING IMPORT UI CHANGES

components.test.tsx already renders ImportDialog with basic interactions. Prefer querying user-visible strings ("Imported", "Failed") over internal classes — Vitest's CSS Modules strategy is non-scoped, so class assertions work but tie your test to implementation detail (Testing & Quality).

Delete flow

  1. TriggerSingle delete from the details dialog, or bulk delete from the selection bar; both open ConfirmDialog from src/components/common/ because the operation is irreversible.
  2. CascadedeleteBook(id) (in core/storage/database.ts) removes the book and all associated rows: content, reading progress, bookmarks, annotations, per-book settings, and the cover. There is no soft delete.
  3. RefreshuseBooks re-reads (and updates its module cache) so counts and cards update without a manual reload.
CONFIRMDIALOG IS THE PATTERN FOR RISKY OPERATIONS

The codebase deliberately routes every destructive or hard-to-undo action (single delete, bulk delete, settings reset) through ConfirmDialog. If you add a risky operation, use it; the pairing of an explicit warning copy plus a non-default destructive button is what keeps bulk mistakes recoverable via backups.

Known gaps and risks

  • No pagination or virtualization. The library renders one flat sorted list — every filtered book has a DOM node with a (lazy-loaded) image. There is no windowing library and no "load more" boundary. Advice: this is fine up to a few hundred books; if you read collections in the thousands, weigh virtualization before assuming the browser will cope with drag reordering plus enough img elements.
  • Drag reorder depends on browser pointer capture support (all modern browsers; setPointerCapture is the whole gesture model). Touch drag on mobile layout is inherently more fragile than mouse drag.
  • Remote covers (isRemote: true) fail offline — the CORS fallback intentionally trades offline reliability for storage (see the warning above). Export considerations for these covers are discussed in Import & Backup.
LONG LIBRARY, DENSE LIST

With no virtualization, a thousand-card grid keeps a thousand coverContainer nodes alive (even with lazy images) and every drag pass re-runs FLIP placement over the whole grid. If you routinely import at that scale, keep backups small per export run and consider archiving finished books — filters reduce the rendered set, so archiving is currently the cheapest "pagination".
