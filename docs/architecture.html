Architecture

WebXReader is a single-page React application with no backend: every feature is a component tree reading from IndexedDB and browser storage. This chapter maps the stack, the folder structure, the routing table, the single provider, the hook layer, and the design-token system so you can navigate src/ without getting lost.

NO STATE LIBRARY — AND THAT IS DELIBERATE (FOR NOW)

The codebase persists everything important in IndexedDB and derives UI state with hooks, so a global store would mostly mirror what useBooks() and SettingsContext already do. If a future feature (say, the reading-statistics dashboard from the roadmap) makes cross-view state unavoidable, reconsider then — do not add a store speculatively.

High-level layers

Read the app top-down like this. Data only ever flows in one direction between layers:

  1. Entrysrc/main.tsx mounts <StrictMode><App/> onto #root with createRoot. No providers at the main level — main.tsx does not wrap App in anything.
  2. Routing shellsrc/App.tsx wraps the route table in SettingsProvider then HashRouter. Route changes mount/unmount whole views; nothing survives except the provider and module-level caches.
  3. Viewssrc/components/ — library/, reader/, settings/ compose the screens. Views own their local interaction state and delegate persistence to hooks.
  4. Hookssrc/hooks/ — the only bridge between components and storage. They own loading/error state and caching.
  5. Domain servicessrc/features/ (import/export/library helpers) and src/formats/ (registry, definitions, engines) do the heavy lifting: parsing, backup, capability queries.
  6. Storage + parsingsrc/core/storage/database.ts wraps IndexedDB; src/core/parsing/ holds the per-format parsers.
  7. Utilitiessrc/utils/ — pure, dependency-free helpers usable from every layer above.

A typical render loop looks like: hash route changes → view component mounts → its hooks call core/storage/database → IndexedDB reads resolve into useState → the view renders → user actions call update functions, which write and re-read. Preferences that are theme/layout/sort-shaped live in the settings row of the database and are hydrated through SettingsContext.

Routing

src/App.tsx verbatim structure:

<SettingsProvider>
  <HashRouter>
    <Routes>
      <Route path="/" element={<LibraryView />} />
      <Route path="/read/:bookId" element={<ReaderView />} />
      <Route path="/settings" element={<SettingsView />} />
      <Route path="/about" element={<InformationPage kind="about" />} />
      <Route path="/privacy-policy" element={<InformationPage kind="privacy" />} />
      <Route path="*" element={<Navigate to="/" replace />} />
    </Routes>
  </HashRouter>
</SettingsProvider>

Practical consequences:

  • Deep links are hash links. The reader route is #/read/<bookId>. Because navigation never leaves index.html, the static host needs no rewrite rules (mirror hosting notes in PWA & Deployment).
  • Unknown URLs fall back home. The * route <Navigate to="/" replace /> replaces history so the back button doesn't ping-pong.
  • Views are remounted per navigation. Reader and library state that must survive a round trip is persisted deliberately — library view state via sessionStorage (Library & Metadata) and reading progress via the debounced progress hook (Reader Engine).

Providers vs hooks: topic boundaries

WebXReader has exactly one provider and five hooks. Knowing which one to reach for stops duplication early.

The single provider: SettingsProvider

src/app/providers/SettingsContext.tsx creates a context from a single useSettings() call and exposes:

{ settings, loading, updateSettings(partial), resetSettings() }

Consume it via useSettingsContext(), which throws 'useSettingsContext must be used within a SettingsProvider' if called outside the tree. Because this context lives around the router, it survives every navigation — that is why global preferences are here and everything else is not.

The hook layer

Hook (src/hooks)ReturnsNotes
useBooks() { books: LibraryBook[], loading, error, refreshBooks(), removeBook(id), removeBooks(ids), toggleFavorite(id), updateReadingStatus(id, status), toggleArchive(id) } LibraryBook = Book & { readingProgress: number } — the progress field is derived from the progress store on read and never written back into the book record. Module-level cache cachedBooks plus invalidateBooksCache() lets the library survive brief navigation away and back. Covers: when a book's coverImage is not a data:/blob: URL, the hook re-fetches getCover(book.id) from the covers store and substitutes the real data.
useSettings() { settings, loading, updateSettings(partial), resetSettings() } Also applies theme immediately via document.documentElement.setAttribute('data-theme', theme) — both in applyTheme() during load and inside updateSettings() when the theme changes. resetSettings() falls back to the system theme (prefers-color-scheme) rather than a hard-coded default.
useReaderSettings(bookId) { settings: EffectiveReaderSettings, globalSettings, bookOverrides, loading, updateReaderSettings(partial), resetBookSettings() } EffectiveReaderSettings has: fontFamily, fontSize, lineHeight, paragraphSpacing, letterSpacing, wordSpacing, textAlign, textIndent, maxContentWidth, contentMargin, readingMode, theme, comicReadingDirection?, comicFitMode?. Merge rule: per-book value wins where present, globals fill the rest — but wordSpacing and theme are always global (see mergeSettings()). readingMode comes from the book override or global.defaultReadingMode.
useBookmarks(bookId) { bookmarks, loading, addBookmark(data), removeBookmark(id), updateBookmark(id, partial) } Bookmarks are kept sorted by createdAt ascending, both on load and after adding.
useReadingProgress(bookId) { progress, loading, updateProgress(partial), flush(), getCurrentProgress() } Persistence is debounced at 2000 ms via a debounce() instance with flush()/cancel(); unmount and book-id changes both flush then cancel so no progress is lost. A status side-effect marks books 'reading' or 'completed' (at overallProgress >= 0.98). The full reader-side contract is in Reader Engine.
WHERE TO PUT NEW STATE

Walk this checklist: (1) purely local UI → useState inside the component; (2) needs to outlive unmount but is user-global → the settings row via updateSettings(); (3) per-book preference → getBookSettings/ saveBookSettings through the useReaderSettings pattern; (4) an entity of its own (a store row) → a new hook over core/storage/database, mirrored in src/types/book.ts and tests. Reach for a context only if multiple routed views need the same live value identical to the provider's.

Other notable pieces of globals.css:

  • ::highlight(webx-search-result) — a CSS Custom Highlight API rule using rgba(250, 204, 21, 0.42), which is how in-book search hits get painted without wrapping DOM nodes (see src/utils/text-search.ts and the search panel).
  • focus-visible ring styles, a styled custom scrollbar, a @media (prefers-reduced-motion) block, and an .sr-only utility.
  • Two sources of data-theme: globally, useSettings.applyTheme sets it on documentElement; locally, ReaderView sets data-theme={readerSettings.theme} on its root element so the reading surface can differ from the shell around it. When you style a new reader component, pick the reader's data-theme scope, not the document one.

Lazy loading & code splitting

The critical path stays small: main.tsx → App → routes imports only the library view eagerly. Reader engines and heavyweight components are loaded with React.lazy inside Suspense in ReaderView, and Vite's manualChunks in vite.config.ts pins each big dependency to its own file so a PDF-only visitor never downloads the EPUB SDK:

ChunkMatched by manualChunks when module id contains…
vendor-epubepubjs
vendor-pdfpdfjs-dist
vendor-zipjszip
vendor-parsermarked or dompurify
vendor-iconslucide-react
vendor-reactnode_modules/react, react-dom, or react-router-dom

The build also sets target: 'es2022' and sourcemap: true; the dev-facing preview command serves the production build on port 4173 with strictPort (so it fails rather than drifting to another port, and the service worker registration logic in deployment can rely on a fixed origin). A reachable summary of what each chunk costs at load time lives in Getting Started; the engine-loading mechanics are in Reader Engine and Formats & Parsers.

Known structural gaps

Honest inventory, so you don't rediscover these the hard way. Facts first, advice marked:

  • DoubleSidedReader is a thin stub. It renders <PaginatedReader pagesPerSpread={2} /> — there is no true two-page spread typography or independent left/right page state yet. The 'vertical' reading mode in ReaderView routes to it.
  • ReaderView is ~1,145 lines and carries roughly fifteen useRef declarations at the top for zoom/wheel/touch bookkeeping. It works, but consider extracting a zoom coordinator before your next feature touches it.
  • Zoom logic is duplicated between PDF and CBZ. PdfReader and CbzReader each implement wheel/pinch zoom handling against the shared readerZoom state in ReaderView; motion semantics can drift between them.
  • Metadata has a dual date field. The format-layer FormatParsedData metadata uses optional publishDate, while the persisted Book entity uses publicationDate; import-service.ts bridges them with params.metadata.publishDate || params.metadata.publicationDate || ''. The duplication is kept for compatibility — see Data Model.
  • No state library. As argued above, this is deliberate for the current feature set, not an omission to fix blindly.
ADVICE: WHEN REFACTORING THESE

Each of the first four items is a good one-feature-per-branch target. The repo's existing branch pattern (see below) plus the test suite (Testing & Quality) gives you a safe harness: run npm test and npm run build before opening a PR, and update the chapter in Developmental/ that described the problem so the docs and code stay in sync.

Adding a feature: branch flow

The repository's existing branch names establish the convention:

Branch examplePattern it demonstrates
feature/book-cover-editorNew UI feature, one branch per feature
feature/reader-settingsFeature scoped to one view
format/cbzFormat additions use format/<ext>
infra/firebase-hostingBuild/deploy work uses infra/<topic>
jules/auditBot- or agent-authored work branches; optimization/set-1 and Exp/set-1 show experiment batches

A new feature branch should follow the same shape: pick feature/<short-slug> (or the matching family prefix), keep one coherent change per branch, and mirror the flow used by past commits — implement, extend src/test/ where behavior is lockable, run npm test, npm run lint and npm run build, then update the relevant Developmental/ notes. If the change touches the storage schema, read Storage & Persistence first because the migration story is version-gated, and export a backup before testing destructive paths (Import & Backup).
