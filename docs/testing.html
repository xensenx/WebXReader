Testing & Quality

WebXReader is tested with Vitest in a jsdom environment backed by a real (well, fake) IndexedDB, so storage tests exercise actual database code paths instead of mocks of the storage layer. This chapter covers the harness configuration, the deterministic mocks in the setup file, all twelve suites with what each one locks down, the fixtures, and lint — plus an honest list of what is not tested.

The Vitest config block

Everything test-related sits inside vite.config.ts itself — there is no separate vitest.config.ts:

test: {
  globals: true,          // describe/it/expect available without imports if preferred
  environment: 'jsdom',
  setupFiles: ['./src/test/setup.ts'],
  css: {
    modules: {
      classNameStrategy: 'non-scoped',
    },
  },
}

The non-scoped strategy is important: CSS Modules class names stay unhashed under test, so a component gets its readable class (e.g. card) instead of a generated mangle like _card_x93kf. That makes class-based assertions possible — but see conventions before using them.

Test setup and deterministic mocks

src/test/setup.ts does four kinds of work:

  1. Enable jest-dom matchersimport '@testing-library/jest-dom/vitest' adds matchers like toBeInTheDocument() to Vitest expect.
  2. Install fake IndexedDBimport 'fake-indexeddb/auto' replaces globalThis.indexedDB wholesale. Every suite path that touches core/storage/database exercises real transactions against an in-memory database — crucial for the storage and e2e suites.
  3. Stub crypto for reproducibilityWhen crypto.randomUUID is missing it is pinned to the fixed value '12345678-1234-4234-8234-123456789abc', and crypto.subtle.digest gets a deterministic 32-byte mock hash (input bytes folded into 32 buckets, mod 256). Same input, same id, same SHA-256 — imports, dedup and backups are comparable across test runs.
  4. Polyfill and patch browser APIsUint8Array.prototype.toHex and Uint8Array.fromHex are polyfilled for jsdom (used by binary/codec paths), and window.matchMedia is mocked to a never-matching object so theme logic code can run.
JSDOM HAS NO REAL PARSER OR CANVAS

jsdom implements no WebP rasterization, no layout, and no service workers. Anything depending on canvas rendering (cover resizing), epub.js iframe rendering, or PDF.js painting must be covered at the unit/integration level rather than end-to-end. That is a structural limitation of this harness, not a gap you should patch by adding "browser tests" into jsdom.

Deep dives

storage.test.ts — the storage contract

This suite is the executable spec of Storage & Persistence. It clears the database in beforeEach and then verifies, against fake-indexeddb:

  • Book CRUD lifecycle: addBook → getBook → listBooks → updateBook → deleteBook, asserting the deleted read returns undefined.
  • Atomic bundle rollback: when metadata cannot be re-added after content exists, the whole book bundle rolls back — the saveBookBundle transactional guarantee rather than per-row best effort.
  • Progress round-trip: saveProgress / getProgress preserving chapter/scroll/page fields.
  • Bookmark listing and deletion.
  • Backup export and restore producing a complete library — the same path the app uses, not a test-only serializer.

Because it clears state between tests, it also makes the fake database safe for other suites, which do their own clearDatabase() — keep doing that in new storage-touching tests.

e2e-workflow.test.ts — one test, whole app

A single it plays out the full lifecycle with a real File built in memory:

StepAssertion
Empty librarylistBooks() starts at 0.
ImportimportFile(txtFile, { autoDetectChapters: true }) succeeds; the preamble plus 2 Chapter X: headings give totalChapters === 3.
Status changeMarking 'reading' persists via updateBook.
ProgresssaveProgress writes chapter/page/scroll fields; getProgress reads them back.
BookmarksaveBookmark then listBookmarks contains it.
Backup v2exportBackup() produces a backup; restoreBackup() resets into it.
DeletedeleteBook leaves the restored library consistent.

Why it matters: any change in the import parser, storage layer, or backup format that breaks the semantics of progress/bookmarks will trip this single suite. It is your cheapest full-system check before refactors.

reader-content-security.test.tsx — the XSS regression suite

This suite exists because readers render untrusted HTML: EPUB chapters are authored files, and restored backups put arbitrary strings into chapter content. The malicious fixture is a chapter containing <script>, inline onclick/onerror/ onload handlers, an <iframe srcdoc>, a javascript: href, and otherwise readable text. Three tests:

  1. Restore-time sanitization: runs restoreBackup(makeBackup([maliciousChapter])), reads the restored content back from the database, and asserts the sanitized DOM contains no script tags, event handler attributes, iframes, or javascript:/external href values — while keeping the readable text intact.
  2. Render-boundary sanitization: renders real components — <ScrollReader> and <PaginatedReader> with the malicious chapter as chapters — and queries each engine's [data-chapter-body="true"] element for the same safety contract.
  3. Malformed record rejection: a backup whose chapter content is not a string is rejected by restoreBackup with "Invalid content payload in backup", and nothing is stored.
NEUTRALIZE, DON'T DISABLE

If a sanitizer change makes one of these tests fail, treat it as a production security bug, not a test to update. The correct change is in src/core/parsing/sanitize-reader-html.ts (DOMPurify configuration), and Formats & Parsers documents which constructor options must stay set.

What a good test looks like here

Real excerpts. From storage.test.ts — note the database-truth style, fixture-in-code, and the atomicity assertion (a failed bundle write leaves the original content in place):

it('rolls back the entire book bundle when metadata cannot be added', async () => {
  await addBook(dummyBook);
  await saveBookContent({ bookId: dummyBook.id, format: 'txt', rawText: 'original' });

  await expect(
    saveBookBundle(dummyBook, { bookId: dummyBook.id, format: 'txt', rawText: 'replacement' }),
  ).rejects.toThrow();

  expect((await getBookContent(dummyBook.id))?.rawText).toBe('original');
});

And the shape of a component test from components.test.tsx: render the component as a user would see it, interact, and assert on the observable outcome (a handler call or visible change) — never on a generated class name.

Guiding rule visible throughout the suite set: assert on what a user can observe (text, roles, handlers, database rows), not on internals.

Linting

npm run lint runs oxlint, configured through .oxlintrc.json at the repo root. It is deliberately lightweight: a fast Rust-based linter covering correctness and style nits, not a full type-checking hook — TypeScript itself (see project references) runs again via tsc -b inside npm run build and is the real type-safety invariant.

ADVICE: LINT BEFORE PR

The CI pipeline (PWA & Deployment) builds and deploys but does not run tests or lint, so run npm run lint && npm test locally before opening anything. There is no pre-commit hook to catch you.

Writing new tests

  1. Lean on fake-indexeddbDo not mock database functions; let suites hit the real (fake) DB and call clearDatabase() in beforeEach/afterEach. Combining database truth with component rendering is how components.test.tsx catches import flow bugs.
  2. Rebuild binary fixtures in codeUse new File([...], name, { type }) or generate archives with JSZip like import-cbz.test.ts. Fixtures in fixtures/ are for manual smoke tests and parser iteration.
  3. Query user-visible text, not classesTesting Library getters like getByRole/getByText survive render refactors. Class-name assertions technically work because of the non-scoped CSS Modules strategy, but break on styling reshuffles — reserve them for genuine styling contracts.
  4. Determinism is freeThe fixed UUID and fake SHA-256 in setup means identical inputs produce identical ids and hashes; write assertions that exploit that (dedup tests, backup equality) rather than randomizing ids yourself.
  5. Put each claim in the right suiteStorage semantics belong to storage.test.ts-style suites; rendering behavior in *.test.tsx; pure parsing in parser tests. One concern per suite keeps failures diagnosable.

Known gaps and honest omissions

  • No Storybook. The project has no component gallery. Component appearance is reviewed manually; if a future contributor wants visual tooling, that is a new decision, not a hidden config to find.
  • No CI test job. The only workflow (.github/workflows/firebase-hosting-production.yml) installs, builds, and deploys to Firebase Hosting — it never runs npm test or npm run lint. Advice: adding a test job to this workflow or a dedicated .github/workflows/test.yml on push/PR would catch regressions before they deploy. Until then, tests only protect people who run them.
  • Formatting and style are not mechanically verified. There is no Prettier and lint covers correctness more than formatting. Advice: match the file you are editing for indentation and layout.
  • Engine internals are unrenderable in jsdom. EPUB.js iframe behavior, PDF.js canvas painting, and CBZ blob decoding have no integrated coverage (see the warning above). When editing engines (Reader Engine), sanity-check manually with real files from fixtures/.
  • Service worker behavior is untested. public/sw.js has no suite; offline behavior is verified manually per deploy (see the ops checklist).
  • No visual/regression layer. Nothing snapshots rendered output; typography regressions in the reader rely on review.
  • Reader hooks are exercised indirectly. Progress persistence, per-book settings merging, and bookmark ordering are locked at the database/parser layer; only a thin slice runs through rendered components. If you refactor useReadingProgress debounce/flush semantics, write a dedicated hook test rather than relying on the e2e suite.
  • No coverage report configured. Vitest can emit --coverage, but the project doesn't wire it, so "untested paths" is tribal knowledge — this chapter is the map.
ADVICE: WHAT TO TEST FIRST WHEN ADDING A FEATURE

For storage-adjacent features (new store, migration, new backup payload), extend storage.test.ts-style coverage — it is the cheapest to write and the most valuable to keep. For UI features, a compact components.test.tsx-style interaction test (render, click or type, assert visible output) is usually enough. Only invest in full e2e lifecycle tests when a feature crosses more than two subsystem boundaries — that is a lot of setup code to maintain in one it().
