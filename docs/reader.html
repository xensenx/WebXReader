Reader Engine

The reading surface is split into a shared shell, ReaderView.tsx, and a set of swappable engines that each render one category of book: ScrollReader, PaginatedReader, DoubleSidedReader, plus the heavyweight EpubReader, PdfReader, and CbzReader engines. This chapter covers how engines are chosen and lazy-loaded, the unified zoom system, keyboard routing, how progress is saved and restored per format, in-book search, and how reader settings are gated by format capabilities.

Routing and composition

The route /read/:bookId is registered under a HashRouter in App.tsx, so deep links like index.html#/read/abc123 work on static hosting without a server rewrite. When the route mounts, ReaderView loads the Book and BookContent records from the database (Data Model) — if either is missing it renders an error state instead of a reader.

The full-screen layout composes four regions:

  1. Hideable headerTitle, header-visibility toggle button, chapter title, fullscreen control, and the zoom controls. Toggled with H or the in-header button.
  2. Engine stageA <div> ref'd as readerStageRef that hosts exactly one active engine instance and carries the capture-phase zoom listeners.
  3. DrawersTableOfContents, BookmarkPanel, SearchPanel, and ReaderSettings. Esc closes all of them in one step; each drawer additionally installs its own window-level Escape listener as a second line of defense.
  4. Progress barThe bottom ProgressBar shows overall progress and accepts a scrub to seek.

Engine selection and lazy loading

Two decisions drive engine selection: which family (fixed-layout engine vs reflowable mode) and which reading mode (scroll, paginated, or vertical). The heavy engines are only downloaded when actually needed: 

const EpubReader = lazy(async () => {
  const module = await import('../../formats/engines/EpubReader');
  return { default: module.EpubReader };
});
/* same for PdfReader, CbzReader */

The three DOM engines — ScrollReader, PaginatedReader, and the DoubleSidedReader stub — are statically imported instead: they are needed by nearly every book format and cost little to bundle.

Selection rules

ConditionEngine
Book is EPUB or PDF or CBZ and content.originalFile is present EpubReader / PdfReader / CbzReader
Those ids but originalFile missing Fall through to the reflowable DOM engines against whatever parsed chapters exist — see the formats warning.
Reflowable, reading mode scroll ScrollReader
Reflowable, reading mode paginated PaginatedReader
Reflowable, reading mode vertical DoubleSidedReader (the stub)
PDF, reading mode vertical Forced to 'paginated': effectiveReadingMode rewrites an unsupported vertical request for fixed-layout PDF.
INFO — CBZ READING DIRECTION RESOLUTION

CBZ page-turn direction resolves as user setting → book metadata → default: readerSettings.comicReadingDirection ?? (book?.identifiers?.readingDirection) ?? 'ltr'. The middle term is exactly where the parser deposits a readingDirection value extracted from the archive — see Formats — CBZ. Fit mode defaults to 'contain' and pageGap seeds from readerSettings.contentMargin.

Unified zoom system

All three zoom-capable engines (EPUB via renderer scaling, PDF and CBZ via re-rendered canvases) share one controller in ReaderView. Zoom is tracked as readerZoom and clamped to format-dependent bounds, declared verbatim at the top of ReaderView.tsx: 

const MIN_READER_ZOOM = 0.5;
const MAX_READER_ZOOM = 3;
const MIN_PDF_ZOOM = 0.24;
const MAX_PDF_ZOOM = 8;

Reflowable books use the READER bounds; fixed-layout books — anything for which isFixedLayout(book.sourceFormat) is true — get the wider PDF bounds, where the 0.24 floor supports reading page-bleed and small print. Ctrl+0 resets to 1.0.

Ctrl+wheel zoom

The ReaderView stage intercepts wheel at capture phase, preventDefault() + stopPropagation(), and only matches events with ctrlKey or metaKey from targets inside the stage. This stops both browser zoom and native scroller interference, then the gesture is routed to the controller. The handler normalizes deltaMode differences into pixels before applying the exponential step:

deltaModeMultiplier applied to deltaY
DOM_DELTA_LINE× 16 (line scroll granularity → pixels)
DOM_DELTA_PAGE× viewport clientHeight (falls back to window.innerHeight when no viewport element)

Then the zoom factor is computed and applied around a cursor pivot:

zoomBy(Math.exp(-delta * 0.0008), latestPoint);

Exponential steps keep the effective zoom relative (each wheel notch multiplies the previous value) instead of adding flat units, so zooming near either bound never produces a jarring one-notch jump.

Zoom anchors (PDF / CBZ)

For fixed-layout stacking, PDF and CBZ share the anchor-pivot protocol: ReaderView captures a snapshot of what the user was looking at — the page element under the cursor and the fractional position within both page and viewport (PdfZoomAnchor / CbzZoomAnchor, re-exported from src/formats/index.ts) — and the engine's previewZoom(zoom, anchor) re-renders pages keeping that exact point stationary. Zoom is applied optimistically as a preview and then committed so rapid wheel gestures do not queue jittered repaints.

Pinch zoom

Two-finger touch gestures on the stage measure the pinch distance and compute startZoom * gesture.distance / start.distance, then the new zoom is fed through a requestAnimationFrame queue that coalesces multiple touchmove events per frame into a single smooth zoom update. Ctrl++ / Ctrl+- keyboard zoom shares the same zoomBy path (factor 1.1 and 1 / 1.1).

Keyboard shortcuts

A single global keydown listener on window dispatches reader-wide shortcuts. It early-returns whenever the event target is an INPUT, TEXTAREA, or contentEditable element, so typing in the search box or a bookmark title never triggers keys like / or b.

In-engine navigation

Arrow and page keys are handled inside each engine, which is why the mapping differs per format:

EngineNextPreviousNotes

Library surfaces also respond to keyboard input: BookCard.tsx, BookList.tsx, and LibraryView.tsx each install their own handler for navigation and open actions. Full per-event detail lives in Library; this chapter intentionally does not duplicate it.

Progress and resume

Saving and restoring positions is funneled through src/hooks/useReadingProgress.ts. The hook's return surface is small: 

return { progress, loading, updateProgress, flush, getCurrentProgress };

Write path

  • Debounced save. updateProgress(partial) merges into the in-memory record and schedules a 2000 ms debounced persist (a new update inside the window coalesces into one IndexedDB write).
  • Book record refresh. When persistProgress runs it also updates the Book record: stamps lastOpenedAt/updatedAt and derives readingStatus — overallProgress >= 0.98 becomes 'completed'; anything above zero becomes 'reading'. The book record is only rewritten when the status actually changed, or when Date.now() - lastOpenedAt > 30000, so library sort order does not churn on every save.
  • React churn control. updateProgress triggers a re-render only when the rounded integer percent, chapterId, or pageIndex actually changes — fractional pixel noise during scrolling is swallowed without state updates.
  • Forced flush. flush() persists immediately and cancels the pending debounce. ReaderView invokes it on bookId change and on unmount via a flushRef indirection, and calls it before navigating to '/', so closing or switching books cannot lose the last-second position.
  • Synced reads. getCurrentProgress() reads a synced ref so callers get the very latest value without a closure-stale progress.

Restore path

Once the content record loads, ReaderView takes the previously-saved ReadingProgress — whose record shape is { scrollPosition, chapterId, pageIndex, epubCfi, overallProgress, readingMode } — and freezes it into initialProgressRef as restoreLocation. It is passed to the selected engine as its initial position, so a book opens exactly where it closed, before any live progress reporting begins. Which fields matter depends on the format:

Format / modeInitial position prop(s)Live progress callback
EPUB (EpubReader) initialCfi={restoreLocation?.epubCfi} handleEpubProgress(cfi, fraction, href) stores epubCfi and matches the TOC chapter by normalized href (strip #; accept equality or endsWith in either direction).
PDF (PdfReader) initialPage={restoreLocation.pageIndex + 1} — 0-based stored → 1-based engine handlePaginatedProgress.
CBZ (CbzReader) Same as PDF: 0-based stored → 1-based engine Same structure as PDF via its own handler; page tracking uses O(log N) binary search over rendered page offsets.
Scroll (TXT/MD/HTML) initialScrollPosition (px), initialChapterId, initialProgressFraction, initialProgressMode Record holds chapterId + scrollPosition + fraction, with reading mode 'scroll'.
Paginated initialPageIndex + fraction Same record fields under a paginated reading mode.
Vertical (DoubleSidedReader) initialPageIndex + fraction Stored under pageIndex via handleDoubleSidedProgress with reading mode 'vertical'.
WARNING — FIXED-LAYOUT BOOKMARK IDS

For fixed-layout formats a bookmark's chapterId is not a chapter id at all: it is the stringified page number, (pageIndex ?? 0) + 1. Jump code parses it back with parseInt(bm.chapterId) and calls pdfReaderRef.current.goToPage(page) / cbzReaderRef.current.goToPage(page). Nothing else may reinterpret chapterId for PDF/CBZ — or delete a bookmark round trip expecting real chapter ids.

Bookmark resume per format

The same per-format positioning extends to bookmarks. EPUB stores a canonical epubCfi and jumps via epubReaderRef.current.goToCfi(bm.epubCfi). PDF and CBZ store the stringified page number above and jump via goToPage(parseInt(bm.chapterId)). Reflowable DOM bookmarks recover from chapterId + scrollPosition (ScrollReader) or pageIndex (PaginatedReader / vertical) exactly like the restore path.

Seeking from the progress bar

The bottom ProgressBar understands a scrub gesture: when the user clicks or drags, onSeek(fraction) fires with the target fraction and ReaderView routes it to the active engine:

  • Handle-based engines. EPUB, PDF, and CBZ engines each expose goToProgress(fraction) on their handle (EpubReaderHandle, PdfReaderHandle, CbzReaderHandle), so a scrub becomes goToProgress(fraction) on the active ref.
  • DOM engines. ScrollReader/PaginatedReader/vertical mode scroll the viewport proportionally: the target fraction is converted into a chapter and pixel/offset position, then applied directly to the scrolling element.

Seek, keyboard arrows on the scrubber, TOC jumps, and manual scrolling all have exactly one internal consumer — updateProgress — which guarantees the persisted record reflects whatever last moved the reading position, regardless of how it moved.

In-book full-text search

Search is powered entirely by pure DOM utilities in src/utils/text-search.ts; no index is kept for text chapters — SearchPanel.tsx scans on demand. The exported API:

FunctionWhat it does
extractDomText(root) TreeWalker over the chapter subtree producing plain text. Skips script, style, noscript, and template nodes; emits '\n' between distinct block tags so word boundaries don't merge paragraphs.
findTextMatches(text, query, maxMatches = 100, compactWhitespace = false) Case-insensitive scan with offset maps linking text offsets back to DOM positions, capped at maxMatches. Optional whitespace compaction so line-wrapped sentences match.
findTextRange(root, query, occurrence = 0) Returns a Range for the Nth match so the panel can select, highlight, and scroll to it precisely.
createTextExcerpt(text, match, radius = 42) Builds the search hit row as { before, match, after } off a ±42-character radius with '…' ellipsis decorators.

SearchPanel composes these: it runs extractDomText → findTextMatches to build result rows (excerpt per hit via createTextExcerpt), then on selection converts the hit to a findTextRange result and scrolls to it. Highlighting is a CSS Custom Highlight API style, rendered via ::highlight(webx-search-result) with rgba(250,204,21,.42) in src/styles/globals.css.

INFO — SEARCH CAPABILITY GATING

Search is not universally available: the search capability flag on FormatCapabilities (see Formats — capability matrix) is false for CBZ, so the search drawer is suppressed for comics. PDF search reports through the pdf.js engine rather than a DOM scan.

Reader settings

Reader settings come from useReaderSettings(bookId), a per-book overlay where per-book values win over globals, with two exceptions: wordSpacing and theme are always global so visual identity stays consistent across book switches. Settings are edited in the ReaderSettings.tsx drawer (~479 lines) — theme (light / dark / sepia), typography, spacing, and per-comic controls — and applied by the shell with a data-theme attribute on the reader root <div>.

Capability gating

The settings drawer asks the registry what a given book can support, using exactly these helpers from src/formats/index.ts: 

const canDoubleSided = doubleSidedSupported &&
  (format ? formatSupportsFeature(format, 'doubleSided') : true);
const canReadingDirection = formatSupportsFeature(format, 'readingDirection');
const canFitMode = formatSupportsFeature(format, 'fitMode');
const canPageGap = formatSupportsFeature(format, 'pageGap');
const canTypography = !isFixed &&
  (format ? formatSupportsFeature(format, 'customTypography') : true);

In practice this means:

FormatHidden in the drawerShown
PDF (fixed layout) Typography: font, line height, text size, paragraph margins (customTypography is false). Reading mode (vertical forced to paginated), zoom, search.
CBZ (fixed layout) Search and typography. The search capability is false, so the search drawer is suppressed entirely. Comic controls: reading direction (LTR/RTL), fit mode, page gap seeded from readerSettings.contentMargin.
EPUB Nothing special. Typography, zoom, search, reading modes — the most complete controls set.
TXT / MD / HTML Zoom (the zoom capability is false — no canvas to scale). Typography, all three reflowable reading modes, search.
DANGER — NEVER BYPASS THE CAPABILITY GATES

Adding a setting control whose visibility is not backed by a formatSupportsFeature check breaks the contract between the registry and the UI. A user could re-open typography controls on a PDF, mutate the stored setting, and hit concrete rendering bugs when the engine ignores the field. Always route through the capability row — if a control has no supporting flag, add one to the format definition first.

Engine internals at a glance

A quick orientation to what each heavy engine actually does at render time — enough to know which file to open, details live in the code and in Architecture:

EngineRender modelPosition tracking
EpubReader epubjs renders book content inside a sandboxed iframe; chapters stream through the renderer as the user moves. Canonical epub CFI strings for progress, restore, and bookmarks.
PdfReader pdf.js canvases per visible page; re-rendered on zoom with the shared anchor-pivot protocol. 1-based page index — always converted at the boundary from the 0-based stored pageIndex.
CbzReader <img> elements fed by lazily-created blob URLs from the stored archive buffer; webtoon scroll, paginated, and double-spread RTL modes. O(log N) binary search over rendered page offsets so figuring out the current page is cheap even mid-flick.
