1. Reading statistics and activity dashboard

Planned; not implemented. The target is a local dashboard of daily/weekly/monthly activity, reading time over time, books completed, pages/chapters read, streaks, history timelines, personal records, and library stats (total books, series, formats, storage). The roadmap is explicit about the direction: "a useful statistics dashboard, not an overly gamified experience".

What exists today: the type is already declared in src/types/book.ts — interface ReadingSession — but nothing writes ReadingSession records: there is no store, no writer, and no UI. ReadingProgress knows where you stopped; it does not know how long you actually read.

Design constraints the roadmap calls out: a lightweight session tracker must handle idle time and prolonged inactivity, avoid counting time when the tab is backgrounded or the reader is idle, recover sensibly from interrupted sessions, and stay local. The existing debounced progress hook (useReadingProgress, 2000 ms debounce with flush-on-unmount — Reader Engine) is a useful timing anchor but measures position, not engagement.

ADVICE: SEQUENCE MATTERS HERE

Design the tracker and statistics data model first (what counts as an active minute, how idle is detected), then the dashboard. Starting at the charts guarantees a re-implementation once the session semantics settle. Also: derive what you can from existing timestamps (lastOpenedAt, importedAt, progress updates) before proposing new IndexedDB stores.

Acceptance ideas: time tracked excludes backgrounded tabs (use Page Visibility); a session survives a crash with bounded loss; dashboard renders from a deterministic derivation of stored sessions; tests lock session math against synthetic input (the fake-indexeddb harness makes this cheap — Testing & Quality).

2. Offline dictionary and vocabulary lookup

Planned; not implemented. Allow readers to look up words without leaving the reader. Nothing exists yet, deliberately: the blocking decision is the dataset — which offline dictionary data (source, licence, packaging) — and whether it installs by download or ships with the bundle. Storage footprint, lookup performance, and a natural in-reading interaction (selection-triggered lookup on text content, hard on paginated/comic surfaces) are follow-on design work.

BUNDLE-SIZE RED FLAG

Dictionary data is a classic way to triple the install size and wreck the service-worker precache list. Treat the dataset like a lazy vendor chunk: keep it out of the static precache (PWA & Deployment), load it on demand, and cache it under runtime caching separate from the shell.

Acceptance ideas: lookup works fully offline once "installed"; licence file vendored; lookup on selectable text in scroll/paginated modes documented; graceful no-entry UX for non-matching locales.

3. Keyboard navigation across reader formats

Verify before "building" this. The roadmap identifies arrow-key navigation as missing across formats, but the codebase has moved on: PaginatedReader, EpubReader and CbzReader handle arrow keys (respecting the comic reading direction for RTL), and ReaderView defines single-key chrome shortcuts — H/F/T/B/S// for toggling UI, plus Ctrl+0/−/+ for zoom. Inventory the shortcuts chapter in Reader Engine, find the engine gaps (e.g. search results navigation, TOC traversal), and write the spec as extension and documentation of existing behavior — not as greenfield work.

Constraints: consistent previous/next semantics per format; no conflict with text selection, form controls, or browser shortcuts; discoverability (shortcut help surface); engine-specific tests rather than assuming one implementation fits all.

4. Ambient audio and focus sounds

Planned; not implemented. Initial categories are locally generated noise — white, pink, brown — via the Web Audio API; music/scene additions (rain, library, night) come later, since those need third-party audio assets. Scope: volume control, playback controls, a timer, and strictly optional/unobtrusive behavior — no external audio services or copyrighted material for v1.

Reality notes from the codebase:

  • Nothing pulls audio into the bundle today, and that shows in how lean the vendor chunks are; keep it that way with a lazy chunk if this lands (lazy loading).
  • The reader shell (ReaderView) is already large; a self-contained AmbientAudio component plus a settings toggle is the least invasive shape.
  • Persisting "on/off + volume" belongs in UserSettings (global preference, not per-book) — follow the provider rules in Architecture.

Acceptance ideas: zero network requests for noise generation; audio stops on tab close; timer honored; feature usable without touching reading controls.

5. Further reading-experience improvements

Status: verify. The roadmap lists possible refinements without committing to scope: series-level progress tracking and next-volume guidance, bookmark/annotation workflow improvements (the data model already supports annotations and labels — Data Model, Reader Engine), accessibility passes, reader customization, import/export robustness, and format compatibility. These build on existing features; treat each as an audit-then-extend task against real usage, not a from-scratch build.

7. Explicit exclusions

The roadmap marks these as done — do not re-file them as gaps: CBZ support; custom library ordering and drag-and-drop; library scroll restoration; storage separation and reset controls; backup-restore XSS/HTML sanitization (hardened, deployed, and guarded by the security test suite — Testing & Quality).

TTS IS DELIBERATELY NOT PLANNED

Text-to-speech was consciously rejected: high-quality offline neural TTS is too demanding in model/runtime size and browser compatibility, and basic browser TTS wasn't good enough to justify inclusion. Please don't open "add TTS" as a missing stub — it is a closed decision, not an omission.

DEPENDENCY COST: KEEP NEW DECODE LIBS IN LAZY CHUNKS

CBZ today is feasible because ZIP support already exists via jszip. .cbr (RAR) and .cb7 (7z) require entirely new decode libraries — each is a bundle-size and maintenance tradeoff. Follow the established pattern: register the format in the registry, add a manualChunks branch (like vendor-epub/vendor-pdf, see Architecture), and lazy-load the engine from ReaderView so the main chunk and the service-worker precache stay small (PWA & Deployment).

Checklist: actually adding a new format

Everything a .mobi-style contribution touches, in order — this is the same set CBZ followed when it landed (format/cbz):

  1. Type layerAdd the format id to book.ts's BookFormat union and to FormatCapabilities/definition types in src/formats/types.ts — the compiler will then point at every switch that needs a case (Data Model).
  2. DefinitionCreate src/formats/definitions/<id>.ts with id, label, extensions, mimeTypes, category ('reflowable' or 'fixed'), requiresOriginalFile, the capabilities object, and an async parse(file). Copy the shape of definitions/cbz.ts.
  3. RegistryImport it into src/formats/registry.ts and add it to FORMAT_REGISTRY; the extension→format map, accept attribute, and dropzones update automatically from the registry entries.
  4. ParserImplement the decode in src/core/parsing/<id>-parser.ts. For HTML-ish formats, run output through the reader sanitization path; never build the chapter DOM at parse time (Formats & Parsers).
  5. EngineText formats reuse PaginatedReader/ScrollReader via the shared shell; fixed layouts get a new engine in src/formats/engines/, lazy-loaded, and wired into the format-dispatch in ReaderView.
  6. Chunk hygieneNew heavyweight decode library → new manualChunks branch so bundling stays lazy (Architecture).
  7. TestsRegistry tests for detection/capabilities (extend formats-registry.test.ts), a parser suite like cbz-parser.test.ts, and an import-integration test like import-cbz.test.ts. Binary fixtures in code, per Testing conventions.
  8. DocsUpdate Developmental/formats-to-be-added.md (remove the row) and this chapter, and add the format to the capability matrix in Formats & Parsers.

Suggested order of attack

The roadmap's tentative sequence (dependency-based, explicitly not final priority):

  1. Keyboard navigationAudit existing per-engine shortcuts (Reader Engine), close the engine gaps, and document the result. Cheapest, uncouples nothing.
  2. Session tracker + statistics data modelPrerequisite for the dashboard; design idle/background semantics before any store work.
  3. Dictionary dataset decisionLicence and packaging research first; prototype lookup UX after a dataset is selected.
  4. Locally generated ambient audioWeb Audio noise with minimal controls; self-contained feature.
  5. Series progress, accessibility, import/export refinementsRevisit based on concrete user needs once the infrastructure above exists.

  1. One feature per branchPick the prefix above matching your change family — feature/ for UI/features, format/<ext> for registry work, infra/ for deployment, fix/<area> or scoped fix(area): commits for bugs.
  2. Verify the gap firstRead this chapter's reality column plus the relevant chapter (Reader, Library, Storage…) so nothing already implemented gets rebuilt.
  3. Update Developmental docsIf you implement, reject, defer, or redesign a roadmap item, edit the source markdown file rather than leaving a stale claim — the doc's own maintenance note asks for exactly this.
  4. Run npm test + npm run buildThe build includes tsc -b type-checking; add tests where the new behavior is lockable (Testing & Quality conventions).
  5. Clean your artifactsThings like docs/null.txt and assets/icons/null are exactly the kind of stray file generated by tooling that ends up committed. Check git status for accidental artifacts — e.g. scratch and build outputs — before committing; scratch/ is untracked tooling workspace, dist/ is generated.

Maintenance of this chapter

The roadmap documents end with explicit maintenance instructions, which apply equally to this page: update items as features are implemented, rejected, deferred, or substantially redesigned; keep confirmed implementation status separate from ideas and proposals; and inspect the codebase before starting any item so existing functionality is not accidentally duplicated. If you resolve an audit item, move it out of the open investigations table and into whichever chapter actually documents the fix — stale roadmap entries are worse than no entries, because they misdirect new contributors.
