Data Model

Every piece of persistent state in WebXReader is defined in a single file — src/types/book.ts — as TypeScript interfaces and string-literal unions. There is no server: these shapes map directly onto IndexedDB object stores (see Storage & Persistence) and the JSON backup format (see Import & Backup). This page is the field-by-field reference for all of them.

Chapter

Chapter is recursive: top-level chapters sit in an array, nested children in children. It appears in two places — the table of contents stored on the Book record (structure only), and BookContent.chapters (structure plus content payloads for text formats).

FieldTypeDescription
idstringUnique identifier within the book
titlestringDisplay title
content?stringChapter body — populated for TXT/MD/HTML; usually omitted in TOC entries
href?stringEPUB spine reference (href into the package)
levelnumberNesting depth, 0 = top-level
ordernumberOrder index among siblings
children?Chapter[]Sub-chapters; recursion is validated to depth ≤ 100 when restoring backups

For PDF and CBZ engines there are no real chapters — chapterId in progress records, bookmarks and annotations holds the stringified page number ((pageIndex ?? 0) + 1) so the same key space works across engines.

The central entity — one record per imported file in the books store, keyed by id (a UUID v4 from crypto.randomUUID() with a string fallback). Metadata, user curation state and reading state all live on this single record.

IndexedDB indexes exist on title, author, contentHash, importedAt, lastOpenedAt, readingStatus, favorite and archived — all non-unique. See the Storage schema table.

How reading status is updated

readingStatus and lastOpenedAt are not written by the reader directly. src/hooks/useReadingProgress.ts computes them each time progress saves:

  1. Progress >= 98%book becomes 'completed'
  2. Progress > 0book becomes 'reading'
  3. Otherwisestatus is left as-is
  4. Write disciplinethe Book record is only rewritten when the status changed or more than 30 seconds passed since the stored lastOpenedAt — avoiding a full record put on every scroll event

BookContent

Book bodies are deliberately split from metadata into the separate bookContent store, keyed by bookId (a 1:1 link). Which fields are populated depends on the format:

FieldTypeDescription
bookIdstringForeign key into books; also the store key
originalFile?ArrayBufferBinary payload for EPUB, PDF and CBZ (formats whose parser declares requiresOriginalFile); kept so the reader engine and "download original" can reuse it verbatim
chapters?Chapter[]Parsed chapter bodies for TXT/MD/HTML
rawText?stringOriginal raw text for TXT, kept so chapter auto-detection can be reprocessed without re-reading the file
formatBookFormatRedundant copy of sourceFormat; validated on restore
WHY THE SPLIT

Listing the library means reading thousands of metadata records — you never want an 800-page ArrayBuffer pulled alongside each row for that. Splitting body payloads into a second store keeps useBooks-style listing cheap; see Architecture → Data flow.

BackupBookContent

The JSON-safe twin of BookContent used inside backups, because binaries and chapter arrays cannot ride in a JSON file directly:

FieldTypeDescription
bookIdstringForeign key into the backup's books array

rawText?stringTXT payload
chapters?Chapter[]Parsed chapters, HTML sanitized on restore
originalFileBase64?stringBase64 of the ArrayBuffer, chunked-safe (toBase64 encodes in 0x8000-byte chunks). Only present in version-2 backups

ReadingSession — declared but unused

The model includes a ReadingSession interface (bookId, startedAt, endedAt, duration in seconds, progressAtStart, progressAtEnd) intended for reading-time statistics.

DECLARED, NOT PERSISTED

No IndexedDB store is created for reading sessions and no code currently writes the type anywhere in src/. Treat it as a reserved roadmap item for reading-stats features — if you build on it, you will also need a DB_VERSION bump and a store migration (see Storage → Opening the database).

Two behaviors worth knowing as you read the settings flow: stored preferences are always normalized as { ...DEFAULT_SETTINGS, ...stored, id: 'global' }, so a newer build can introduce fields without a data migration; and if you never picked a theme, the app initializes to the system theme rather than the 'light' default.

BookSettings (per-book overrides)

A per-book delta record in the bookSettings store, keyed by bookId. Every tuning field is optional — only bookId and updatedAt are required — so the record usually contains just the few values you changed for that one book:

FieldTypeNotes
bookIdstringStore key; foreign key into books
readingMode?ReadingModeOverrides defaultReadingMode
fontFamily? / fontSize?string / numberTypography overrides
lineHeight? / paragraphSpacing?numberRhythm overrides
letterSpacing?numberpx
textAlign?TextAlignmentAlignment override
textIndent?numberem
maxContentWidth? / contentMargin?numberLayout overrides
comicReadingDirection?ComicReadingDirection'rtl' for manga-style reading
comicFitMode?ComicFitModeCBZ page fit
updatedAtnumberMillisecond timestamp
NOT OVERRIDABLE

There is deliberately no wordSpacing override, and theme is always global. useReaderSettings(bookId) merges global UserSettings with the per-book BookSettings record, taking the per-book value for any field the book defines, but always resolves wordSpacing and theme from the global settings. The update type omits both fields, so UI code cannot even attempt them.

How the entities relate

Everything hangs off Book.id. There are exactly two recursive/array entities (Chapter inside books) and no many-to-many links. In words:

  • Book 1 : 1 BookContent — the body, keyed by bookId in the bookContent store. Created and saved in the same atomic transaction as the book at import time.
  • Book 1 : 1 ReadingProgress — the position, keyed by bookId in progress.
  • Book 1 : 1 BookSettings — the per-book delta, keyed by bookId in bookSettings.
  • Book 1 : 1 cover — a { bookId, data } record in the covers store; Book.coverImage mirrors it for display.
  • Book 1 : N Bookmarks and Book 1 : N Annotations — ordinary records keyed by their own id, with a bookId index used for listing and cascading deletes.
  • Chapter never gets its own store — it exists as a tree inside Book.tableOfContents (structure) and BookContent.chapters (bodies).
// One-way linkage: every store except `settings` is keyed by or indexed on Book.id
Book(id) ── 1:1 ──> bookContent(id := bookId)
Book(id) ── 1:1 ──> progress(id := bookId)
Book(id) ── 1:1 ──> bookSettings(id := bookId)
Book(id) ── 1:1 ──> covers(id := bookId)      // { bookId, data }
Book(id) ── 1:N ──> bookmarks(index: bookId)
Book(id) ── 1:N ──> annotations(index: bookId)

This is not enforced by foreign keys — IndexedDB has none — it is maintained by application code, most importantly deleteBook(), which removes all seven dependent records in one transaction (see Storage → Atomic transactions).

Derived, not persisted: LibraryBook

Library UI code works with LibraryBook = Book & { readingProgress: number } (src/hooks/useBooks.ts). The added readingProgress field is computed at query time — 1 for completed books, otherwise overallProgress from the matched progress record — and is stripped before every write so the derived value never leaks into the books store. If you are persisting a Book-shaped object yourself, remember to destructure it out, exactly as the hook does:

const { readingProgress: _readingProgress, ...storedBook } = book;
await updateBook(storedBook);
RULE OF THUMB WHEN ADDING FIELDS

Keep src/types/book.ts the single source of truth, remember that Book records created before your change lack the new key (prefer defaults over noUnusedLocals-safe assumption of presence), and if a change requires an index, plan DB_VERSION work in database.ts — object stores and indexes are only created inside the onupgradeneeded handler. Backups gain compatibility concerns too: restoreBackup validates minimal field sets, so additive optional fields are safe, renames are not.
