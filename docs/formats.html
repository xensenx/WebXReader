Formats & Parsers

Every format WebXReader can open is declared in a single static registry. That registry is the one source of truth for extensions, MIME types, reader capabilities, and the parsing step that turns a raw File into normalized Chapter data. This chapter documents the registry API, walks through each format's parsing pipeline, and shows you how to add a new format without touching any other subsystem.

The registry as a single source of truth

src/formats/registry.ts holds a static FORMAT_REGISTRY mapping each BookFormat id to its FormatDefinition, plus a lowercase EXTENSION_TO_FORMAT_MAP built at module load by walking every definition's extensions array. Nothing else in the codebase is allowed to hard-code a file extension: import dropzones, file dialogs, export download names, and the reader UI all query this module.

Registry API

FunctionSignatureBehavior
getFormat (id) => FormatDefinition | undefined Lookup by id; accepts string and returns undefined for unknown or missing ids.
getRequiredFormat (id: BookFormat) => FormatDefinition Same lookup but throws new Error("Unsupported book format: ${id}") when the id is not registered. Use inside code paths that cannot proceed without a definition.
detectFormatFromFilename (filename) => FormatDefinition | null Extracts the extension via getFileExtension, lowercases it, and resolves through EXTENSION_TO_FORMAT_MAP. Returns null when unknown.
getAllFormats () => FormatDefinition[] All definitions in registration order: txt, markdown, html, epub, pdf, cbz.
getAllSupportedExtensions () => string[] Every registered extension without a leading dot, e.g. txt, markdown, md, html…
getAcceptAttribute () => string Dot-prefixed, comma-joined extension list for <input type="file" accept>, in registry order (full list below).
getFormatMimeType (format) => string Returns the definition's first declared MIME type, falling back to application/octet-stream.
isFixedLayout (format?) => boolean true only when the definition's category is 'fixed-layout' (currently PDF and CBZ). Reader zoom bounds and typography controls key off this.
formatSupportsFeature (format?, feature: keyof FormatCapabilities) => boolean Capability query used to enable/disable reader UI controls per book. Unknown formats return false.

The accept string is derived entirely from the registry, so adding a format to the registry automatically extends every file picker in the app: 

// getAcceptAttribute() output after registration order is applied
".txt,.md,.markdown,.html,.htm,.xhtml,.epub,.pdf,.cbz"

TIP

When you change any row of the capability matrix, the only files that should need to move are the format definition itself and the engine that renders it. UI code is forbidden from branching on book.sourceFormat directly — it must go through formatSupportsFeature or isFixedLayout.

Plain Text (TXT)

The simplest reflowable format. Declared in src/formats/definitions/txt.ts with extensions ['txt'] and MIME types ['text/plain']. It parses the file with no external dependencies and produces chapters purely from text heuristics.

Parse pipeline

  1. Read as textreadFileAsText(file, context.textEncoding) decodes the raw file, honoring the encoding the user chose at import (auto-detected by default).
  2. Split into chaptersparseTxt(text, { autoDetect: context.autoDetectChapters ?? true }) from src/core/parsing/txt-parser normalizes line endings and segments the text.
  3. Build TOCThe definition maps each parsed chapter into a Chapter TOC entry with id, title, level, and order.
  4. Return parsed data{ metadata: {}, tableOfContents, chapters, rawText }. Plain text declares no metadata; the whole source text is preserved as rawText for re-chunking later without re-reading the file.

TXT parser internals

core/parsing/txt-parser.ts does three things worth knowing when debugging a badly segmented import:

  • Encoding and line-ending normalization. UTF-8/UTF-16 byte order marks are stripped (when not requested explicitly via textEncoding), CRLF and lone CR sequences are normalized to LF so chapter-splitting logic and scroll math see one consistent representation.
  • "Chapter X" heading detection. Lines that begin conventional chapter markers ("Chapter 3", "CHAPTER TWELVE", numbered forms) become chapter boundaries and titles.
  • ALL-CAPS blank-line headings. A short, fully uppercase line separated by blank lines on both sides is treated as a chapter heading — the classic Gutenberg/ASCII-fiction convention. This means a novel with no explicit "Chapter" markers still segments correctly.
INFO — AUTODETECTCHAPTERS SEMANTICS

FormatImportContext.autoDetectChapters defaults to true and is ??-coalesced at the definition level, so the parser never sees undefined. When the user disables chapter detection at import, the whole file becomes a single chapter with the book title, TOC entries are not generated from headings, and rawText is still stored so the choice can be re-applied later without re-reading the file.

Markdown (MD)

Declared with extensions ['md', 'markdown'] and MIME types ['text/markdown', 'text/x-markdown']. Its definition follows the same reflowable, text-first shape as TXT — same capability row, same readFileAsText entry — but the parser is richer: it extracts structured metadata before splitting content.

Parse pipeline

  1. Read as textreadFileAsText(file, context.textEncoding), exactly like TXT.
  2. Extract YAML frontmatterparseMarkdown from core/parsing/markdown-parser lifts a leading YAML block into metadata: title, author, language, and publisher are picked up when present.
  3. Split on headingsThe document is segmented at H1 and H2 headings. H1 starts chapters; H2 creates sub-chapters at the next TOC level.
  4. Return parsed data{ metadata, tableOfContents, chapters, rawText } — the full markdown source is retained as rawText.

Because rawText keeps the original markdown (frontmatter included), re-imports with different chapter-detection settings can reuse the stored text instead of asking the user for the file again.

HTML Document

Declared with extensions ['html', 'htm', 'xhtml'] and MIME types ['text/html', 'application/xhtml+xml']. Parse mirrors the Markdown flow: readFileAsText → parseHtml(text) → { metadata, tableOfContents, chapters, rawText }, with the HTML parser collapsing tags into chapter content and deriving the TOC from the document's own heading structure. This pipeline also serves the import flow's batch conversion path — see Import & Export for the surrounding UI.

EPUB

The flagship reflowable format. Declared with extensions ['epub'], MIME type ['application/epub+zip'], requiresOriginalFile: true, and zoom: true — the only reflowable format with zoomable rendering. Its parse pipeline is the first one that keeps binary state.

Parse pipeline

  1. Read as ArrayBufferreadFileAsArrayBuffer(file) loads the raw zip container into memory.
  2. UnzipparseEpub(arrayBuffer) from core/parsing/epub-parser opens the archive with JSZip and inspects the entries.
  3. Resolve the OPF packageMETA-INF/container.xml points at the OPF package document, which is parsed to classify zip entries into OPF classed/manifest/spine roles — the authoritative reading order.
  4. Map manifest hrefsSpine item references are resolved against the manifest so each spine entry maps to its actual zip path, with relative-path handling so nested folders (e.g. OEBPS/Text/) resolve correctly.
  5. Extract the TOCNavigation is pulled from an EPUB3 nav document or an EPUB2 NCX file. The resulting TOC is built recursively into a Chapter tree that preserves nesting levels rather than flattening.
  6. Detect the coverThe parser inspects package metadata and manifest entries to find the most representative cover image, surfaced as coverImage.
  7. Keep the original fileThe input ArrayBuffer is returned as originalFile, and requiresOriginalFile: true marks it as mandatory — see the callout below.

EPUB engine

EPUB rendering is delegated to src/formats/engines/EpubReader.tsx, which uses epubjs to run book content inside a sandboxed iframe and tracks reading position as a canonical CFI string — the same identifier used for bookmarks and resume. The CFI is the only position format precise enough to survive typography changes, which is why EPUB progress is stored per-position instead of per-chapter. Engine internals, zoom bounds, and keyboard routing for the EPUB path are covered in the Reader Engine chapter.

PDF

The first fixed-layout format: category: 'fixed-layout', requiresOriginalFile: true, and notably customTypography: false — the reader must never offer font or line-height controls for PDF, since layout is fixed at the byte level.

Parse pipeline

  1. Read as ArrayBufferreadFileAsArrayBuffer(file).
  2. Initialize pdf.jscore/parsing/pdf-init (imported by pdf-parser.ts) configures the pdf.js library and its worker; parsing then follows the standard engine initialization path so import and open share one setup.
  3. Parse metadata and pagesparsePdf(arrayBuffer) reads document metadata (title, author, description, publish dates where present) and builds a tableOfContents from the PDF's declaration entries when available.
  4. Extract the coverFirst-page art is rendered to a data URL and returned as coverImage.
  5. Keep the original fileAs with EPUB, the ArrayBuffer is returned as originalFile and is mandatory — PDF pages are rendered live from it, not pre-extracted to text chapters.
INFO — NO TEXT-CHAPTER RECOMPUTE

The PDF parser does not attempt to replace the original file with extracted text the way some converters do. The document stays as-is, which keeps zoom/search/layout exactly as the publisher rendered them and enables a lossless original-file download.

CBZ Comic Book Zip

The second fixed-layout format, and the only one with comic-grade capabilities: readingDirection, fitMode, and pageGap are all true here and nowhere else. Declared with extensions ['cbz'] and MIME types ['application/vnd.comicbook+zip', 'application/x-cbz'].

Parse pipeline

  1. Read as ArrayBufferreadFileAsArrayBuffer(file).
  2. Unzip and filter imagesJSZip opens the archive; parseCbz filters entries by file extension so only real page images are kept. Non-image members such as ComicInfo.xml and thumbnail directories are ignored for page ordering (but see the metadata step).
  3. Natural-sort the pagesEntries are ordered with a naturalCompare comparator, so page2 sorts before page10 — the classic failure of plain lexicographic sorting.
  4. Read ComicInfo.xmlComicInfo metadata (title, series, volume, issue, notes) is lifted into metadata when present, including identifiers and volume info.
  5. Handle reading directionparseCbz returns a readingDirection value; the definition merges it into metadata.identifiers.readingDirection so it persists as book-level state and drives right-to-left manga page turns inside the engine.
  6. Build the TOCThe table of contents comes from the archive's own bookmarks entries when they exist; otherwise the parser enumerates directory structure and issues sequential numbering so every page is reachable from the drawer.
  7. Extract the coverCover detection is built into the parser — the first sorted page (or declared cover entry) is turned into a cover image for the Library grid.

CBZ engine

src/formats/engines/CbzReader.tsx renders pages in three modes — webtoon continuous scroll, paginated, and a double-spread right-to-left manga mode — with lazy blob URL creation for large issue archives, O(log N) binary search to keep page tracking cheap while scrolling thousands of image entries, and cursor-pivot Ctrl+wheel zoom. The handle types CbzReaderHandle and CbzZoomAnchor are re-exported from src/formats/index.ts. Full details are in the Reader Engine chapter.

WARNING — REQUIRESORIGINALFILE

EPUB, PDF, and CBZ all declare requiresOriginalFile: true. For those formats the raw ArrayBuffer is stored back into BookContent by the database layer instead of just parsed text. This is what enables three features text formats cannot have: (1) the original-file download in Library view, (2) the live engines that render pages from the original bytes (PDF, CBZ, EPUB inside epubjs), and (3) resume that reconstructs exact positions. If you forget to return originalFile from your parser, the book will import but the reader will silently fall back to a degraded reflowable view.

Content sanitization

Because parsed chapters are ultimately rendered as HTML inside the reader, WebXReader treats chapter markup as untrusted input no matter where it came from.

  • Render-time. core/parsing/sanitize-reader-html.ts wraps DOMPurify with the allowed-tag allowlist used when a chapter is injected into the ScrollReader / PaginatedReader DOM tree — see Architecture for where this sits relative to rendering.
  • Restore-time. When a chapter is restored from a backup, the database layer runs sanitizeRestoredChapter inside database.ts so anything re-reading from index also passes through DOMPurify. Chapters stored before the sanity pass, or modified by a future editor, get a second defense-line.
  • Fall-back sanitizer. src/utils/index.ts exports a lighter sanitizeHtml that strips <script> nodes, wildcard on* event handlers, javascript: hrefs, and non-image data: sources. It exists as a defense line when DOMPurify's full parse is not worth the cost.

The cross-suite security suite that pins all three behaviors with tests lives in Testing — reader-content-security. If you add a new format that parses HTML out of a file (like EPUB or CBX variants), your parser must return content that passes those tests verbatim.

Future formats

Formats on the pre-roadmap — RTF, CBR, CB7, MOBI, FB2, DjVu, and XPS — are tracked in Roadmap — formats (Developmental/formats-to-be-added.md in the repository). Each new one lands as another FormatDefinition in the static registry and another parse module under src/core/parsing/; the "adding a new format" walkthrough below is designed to be the actual checklist for those.

Adding a new format

A new format touches four things and nothing else. These steps use real field names from FormatDefinition, FormatCapabilities, and FormatParsedData so you can copy straight from a live definition.

  1. Implement the parserCreate src/core/parsing/<format>-parser.ts exporting parse<Format>(input) => Promise<FormatParsedData>. Read the source file yourself — do not delegate file reads to the registry. If your format needs binary state later (engines, original-file download), return the input as originalFile.
  2. Declare the definitionCreate src/formats/definitions/<format>.ts exporting a FormatDefinition constant. Every field is required except requiresOriginalFile and the optional FormatCapabilities flags.
  3. Register itImport your definition into src/formats/registry.ts and add one row to FORMAT_REGISTRY. The EXTENSION_TO_FORMAT_MAP, the file-input accept attribute, detection, MIME lookups, and Library grids all update from that single line — no other changes.
  4. Update types and testsIf your format introduces a new capability flag, extend FormatCapabilities in src/formats/types.ts and wire it into the reader UI. Add parse round-trip tests to the format suite under Testing.

Here is a real skeleton matching the actual shape of the existing definitions:

// src/formats/definitions/mobi.ts
import type { FormatDefinition, FormatParsedData, FormatImportContext } from '../types';
import { readFileAsArrayBuffer } from '../../utils';
import { parseMobi } from '../../core/parsing/mobi-parser';

export const mobiFormat: FormatDefinition = {
  id: 'mobi',
  label: 'MOBI Book',
  extensions: ['mobi'],
  mimeTypes: ['application/x-mobipocket-ebook'],
  category: 'reflowable',
  requiresOriginalFile: true,
  capabilities: {
    continuousScroll: true,
    paginated: true,
    doubleSided: false,
    zoom: false,
    search: true,
    customTypography: true,
  },
  async parse(file: File): Promise<FormatParsedData> {
    const arrayBuffer = await readFileAsArrayBuffer(file);
    const { metadata, tableOfContents, chapters } = await parseMobi(arrayBuffer);

    return {
      metadata,
      tableOfContents,
      chapters,
      originalFile: arrayBuffer, // enables download + engine rendering + resume
    };
  },
};

And the addition to the registry (the only edit besides the new files):

import { mobiFormat } from './definitions/mobi';

const FORMAT_REGISTRY = new Map<BookFormat, FormatDefinition>([
  ['txt', txtFormat],
  ['markdown', markdownFormat],
  ['html', htmlFormat],
  ['epub', epubFormat],
  ['pdf', pdfFormat],
  ['cbz', cbzFormat],
  ['mobi', mobiFormat], // registry order feeds detection and accept lists
]);

Also extend BookFormat in src/types/book.ts with the new union member so id type-checks — the registry's Map<BookFormat, ...> key type keeps you honest about this at compile time.

TIP — REVIEW THE CAPABILITY ROW FIRST

Before writing parser code, decide on the capability row. It changes downstream UI in ReaderSettings immediately: typography sliders only render when customTypography is true, comic controls only show for readingDirection/fitMode/pageGap formats, and zoom arrow buttons reference isFixedLayout bounds. Committing the capability table first surfaces UX gaps before parse code exists.
