Import & Backup

Two services own the movement of books in and out of the library: src/features/import/import-service.ts turns a dropped file into a validated, hash-deduplicated Book + BookContent pair, and src/features/export/backup-service.ts moves the whole library (or one book) out as JSON/binaries and back in. Both sit on the storage layer described in Storage & Persistence.

The import pipeline

importFile(file, options?) runs one file through nine fixed steps. Every step is fail-fast and returns a structured ImportError rather than throwing, which lets the multi-file import dialog collect per-file outcomes:

  1. Reject empty filesonly file.size === 0 is rejected, with 'The selected file is empty (0 bytes.)'. There is no hard maximum size — see the warning callout below.
  2. Detect formatdetectFormatFromFilename(file.name) looks the extension up in the format registry (Formats). Unknown extensions return an error listing every supported extension via getAllSupportedExtensions().
  3. Read the bufferreadFileAsArrayBuffer(file) — needed for hashing and, for binary formats, kept as the stored payload.
  4. Hash itcomputeHash() produces the contentHash: SHA-256 via crypto.subtle.digest, rendered as hex (src/utils/index.ts).
  5. Dedupunless forceImport is set, findBookByHash(hash) checks the library; a match short-circuits to { success: true, isDuplicate: true, existingBookId }.
  6. Allocate an idgenerateId() — a UUID v4 (crypto.randomUUID() with a fallback).
  7. ParseformatDef.parse(file, { autoDetectChapters, textEncoding }) produces metadata, a table of contents, chapters and optionally a cover. Parsing failures are reported as "Failed to parse <FORMAT> file: …". Format-specific behavior is documented in Formats.
  8. Build the recordsa normalized Book and a BookContent (field defaults in Import defaults; originalFile is the parser-delivered binary or the raw buffer when the format declares requiresOriginalFile).
  9. Persist atomicallysaveBookBundle(book, content, coverData?) writes everything in one IndexedDB transaction; on abort the whole import is rolled back (Storage → Atomic transactions).
// The result union you get back:
interface ImportSuccess {
  success: true;
  book: Book;              // the imported record — or the EXISTING book for duplicates
  isDuplicate: boolean;
  existingBookId?: string; // set only when isDuplicate is true
}
interface ImportError { success: false; error: string; }
type ImportResult = ImportSuccess | ImportError;

interface ImportOptions {
  autoDetectChapters?: boolean; // default true  — TXT chapter detection
  forceImport?: boolean;        // default false — skip the duplicate check
  textEncoding?: string;        // optional decoder label for text formats
}

The UI layer (src/components/library/ImportDialog.tsx) queues multiple files, surfaces per-file results, and shows a size warning once a file passes the threshold from settings.

Size validation and the warning threshold

Validation is deliberately minimal:

NO HARD SIZE CAP

The only rejection based on size is 0 bytes. Large files are handled by an advisory, not a gate: when a file exceeds UserSettings.importSizeWarningMB (default 50 MB, clamped to 1–5000 in the settings UI) the import dialog shows a warning, and you can still proceed. Full-binary parsing of big EPUB/PDF/CBZ files happens entirely in the browser, so the practical limiter is memory, not code — as advice, import multi-hundred-MB files one at a time and consider whether you need the original binary at all before turning on formats that keep it.

Deduplication & forceImport

The dedup key is the SHA-256 of the file bytes, stored on the book as contentHash and indexed in IndexedDB. Consequences worth internalizing:

  • Byte-identical files dedup. The result is still success: true, but isDuplicate carries the existing book — the dialog highlights this case rather than adding a second copy.
  • Any byte change breaks dedup. Re-saving a TXT with a different newline convention or an EPUB with repacked metadata yields a different hash and imports as a new book. If you expect "same book, repacked" to dedup, it will not — the hash is of the file, not the title or ISBN.
  • forceImport: true skips step 5 entirely, producing a genuine second copy with its own id. The restore path (below) does the analogous check against both id and contentHash.

Downloading a library backup

downloadLibraryBackup() calls exportBackup(), serializes with JSON.stringify(backup, null, 2), and triggers a download named webxreader-backup-YYYY-MM-DD.json (UTC date from the current timestamp). The blob is typed application/json and its object URL is revoked 2 seconds after the synthetic anchor click. The full field-by-field spec of the JSON lives in Data Model → BackupData; version-specific differences are what matter here:

AspectVersion 1Version 2 (current)
contents arrayabsent — backups carry metadata, progress, bookmarks, annotations and settings onlypresent — JSON-safe payloads per book
Binary original files (EPUB/PDF/CBZ)not representableoriginalFileBase64 per content record
Text payloadsnot representablerawText / chapters per content record
Accepted by restoreyesyes
Restore when no matching contents entry existsBook restores without a body, and an error string is pushed ("Backup does not contain content for …")Book restores without a body, with no error string

Internally, binaries are encoded by toBase64 in 0x8000-byte (32 KiB) chunks accumulated through String.fromCharCode before one btoa call — chunking avoids blowing the call stack on large arguments; decoding is the mirror operation (atob plus an explicit byte-wise copy into a new ArrayBuffer). The exact helpers are shown in Storage → base64 encoding helpers.

The filename logic, verbatim in intent:

const dateStr = new Date().toISOString().split('T')[0];          // UTC date
const filename = `webxreader-backup-${dateStr}.json`;             // e.g. webxreader-backup-2027-10-30.json
const json = JSON.stringify(backup, null, 2);                     // pretty-printed, 2-space indent
const blob = new Blob([json], { type: 'application/json' });
// synthetic <a download> click; object URL revoked after 2 seconds
Can you hand-edit a backup file?

Yes, within limits — restore validation is structural, not cryptographic. Practical guidance:

  • You may remove whole entries from books, progress, bookmarks, annotations or bookSettings; orphaned child records for removed books are filtered out automatically during restore anyway.
  • You may edit text fields such as titles, tags or note strings.
  • You must keep the structure intact: version (1 or 2), the exportedAt number, all top-level arrays present (possibly empty), and every book's id, title, contentHash and sourceFormat — isBookRecord() rejects anything else, and a malformed book is skipped rather than imported.
  • Never hand-edit originalFileBase64 — a stray character corrupts the binary payload, and the decode failure fails the whole restore.
  • Be aware that imported files you change this way still do not re-derive contentHash, so a *modified title* book retains its real dedup identity.

The UI layer (src/components/library/ImportDialog.tsx) wraps the service in a multi-file workflow — see The import dialog.

Expected failures are never thrown across the service boundary — importFile resolves with { success: false, error }. Only genuinely unexpected conditions land in the catch-all branch. Callers should branch on result.success, not on try/catch.

The import dialog queue

ImportDialog maintains a file queue rather than one-at-a-time processing: you can drop a whole folder's worth of mixed-format files, and each entry resolves to its own ImportResult so one bad file does not abort the batch. Two settings-driven behaviors per entry:

  • A size warning appears when a file exceeds settings.importSizeWarningMB (default 50 MB) — advisory only, and the threshold is configurable 1–5000.
  • Dedup results get a dedicated modal: on isDuplicate the dialog opens a "Duplicate Book Detected" panel naming the existing book — "A book with matching content already exists in your library" — and offers either skipping or importing anyway (the latter re-invokes importFile with forceImport: true for that file). Queue rows afterwards are labeled Imported, Skipped duplicate, or Failed.

Under the hood the queue relies on the same primitives featured in the pipeline table above — the mechanics are unchanged per file.

Hash & id helpers behind the pipeline

Two tiny utilities from src/utils/index.ts carry all of the identity semantics — worth reading in full because so much downstream behavior (dedup, restore skipping, cascade deletes) keys off their outputs:

// Identity: UUID v4, with a string-template fallback for older environments
export function generateId(): string {
  if (typeof crypto !== 'undefined' && crypto.randomUUID) {
    return crypto.randomUUID();
  }
  return 'xxxxxxxx-xxxx-4xxx-yxxx-xxxxxxxxxxxx'.replace(/[xy]/g, (c) => {
    const r = (Math.random() * 16) | 0;
    const v = c === 'x' ? r : (r & 0x3) | 0x8;
    return v.toString(16);
  });
}

// Dedup identity: SHA-256 of the exact file bytes, as a hex string
export async function computeHash(data: ArrayBuffer): Promise<string> {
  const hashBuffer = await crypto.subtle.digest('SHA-256', data);
  const hashArray = Array.from(new Uint8Array(hashBuffer));
  return hashArray.map((b) => b.toString(16).padStart(2, '0')).join('');
}
Why hash the raw file instead of parsed content?

Hashing the ArrayBuffer before parsing keeps the check format-agnostic and cheap — the digest of the same file is deterministic no matter which parser would have handled it, and the result doubles as a stable, indexable string column on every Book. Hashing parsed chapter text instead would mean running the full parser just to detect a duplicate, and would make binary formats (EPUB, PDF, CBZ) awkward to fingerprint meaningfully. The trade-off, as noted in dedup, is that semantics-equal files with byte differences count as different books.

Restoring a backup

restoreLibraryBackup(file) reads the file as text, JSON.parses it (a parse failure surfaces as "Failed to parse backup file: …") and hands the object to restoreBackup() in database.ts. The step-by-step mechanics are in Storage → The restore path; the user-visible contract:

  • Restore is additive and duplicate-safe. Books whose id or contentHash already exists are skipped and noted in the returned errors strings — resetting your library first is not required, and skipping is reported as information, not failure.
  • Everything per-book is scoped to restorable books. Progress records, bookmarks, annotations and per-book settings only re-attach if their bookId belongs to a book that survived dedup, so nothing references a book that is not there.
  • The restore is one atomic transaction. Any error aborts and rolls back all writes; partial installs are impossible. Global settings are applied afterwards, on success only.
  • Version handling. Both v1 and v2 envelopes are accepted; v1 books restore their metadata and annotations but no bodies — appropriate for metadata-only backups.
  • Content is sanitized. Every restored chapter body passes sanitizeReaderHtml(); the security reasoning is in Storage → restore path.
TITLES CAN RESOLVE DIFFERENTLY / COVERS DO NOT TRAVEL

Two practical notes when moving between devices: restored books keep their stored readingStatus and progress, so do not expect them to show as unread; and BackupData has no cover field — covers regenerate only where the format provides them, so a restored book may briefly lack a cover image until appropriate handling regenerates one.

Exporting a single book

downloadOriginalBook(bookId) grabs the book and its content record and picks the best available representation — this is the "export original" action in the library UI:

PrioritySource payloadDownload
1content.originalFileThe original binary, typed via getFormatMimeType(book.sourceFormat); filename is book.originalFilename
2content.rawTextPlain text, text/plain;charset=utf-8
3content.chaptersReconstructed text: chapter titles prefixed, HTML tags stripped via /<[^>]+>/g → '\n', runs of 3+ newlines collapsed to a blank line, chapters joined with '\n\n--- \n\n'
—none of the abovethrows 'No exportable content available for this book.'

Missing book or content records throw "Book or book content not found". Note the asymmetry with the dedup discussion: this reconstruction path is why even v1-backup-restored TXT books (no rawText, but chapters present) can still be exported — they just export as reconstructed plain text, not the original file.

Practical workflows

  1. Set up a backup habitExport a JSON backup after significant import or highlight sessions, and archive the file somewhere the browser cannot evict. As advice, add the date from the filename to your diligence check rather than overwriting one file — versions accumulate.
  2. Move to a new deviceExport v2 on the old browser, then restore on the new one. Restored books keep their ids and hashes, so — after optionally importing the same files if you did not back up contents — dedup will not create double copies.
  3. Replace a book's fileThere is no replace-in-place path. Import with forceImport (or after editing the old copy out), accepting that a second library entry exists; bookmarks and annotations do not migrate between the two ids.
  4. Test round-tripsImport → annotate → export → delete book → restore is the shortest loop that exercises hash dedup, restore sanitization, and error reporting at once. The automated equivalents live in the storage and backup suites — see Testing & Quality.
