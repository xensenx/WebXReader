PWA & Deployment

WebXReader is a hand-rolled PWA: a service worker seeded from the built index.html, a minimal web manifest, and a Firebase Hosting deploy wired through GitHub Actions with Workload Identity Federation — no repo secrets. Because all routes are hash fragments, any static host serves the build as-is. This chapter explains each strategy, the pipeline, and the cache-versioning discipline that keeps deploys coherent.

PWA architecture

Three files in public/ make the app installable and offline-capable, all copied verbatim into dist/ by Vite:

FileRole
public/sw.jsApplication-shell service worker (strategies below).
public/manifest.jsonWeb app manifest for installability.
index.htmlInline script that registers the SW on http(s), un-registers it on localhost, and sets meta theme-color.

Service worker strategies

sw.js is versioned by a single constant — bump it whenever cached assets change:

const CACHE_NAME = 'webxreader-shell-v5';

The behavior, top to bottom:

  1. installCalls self.skipWaiting() immediately, then discovers shell assets: it fetches index.html with cache: 'no-cache', seeds favicon.ico, webxreader.svg, manifest.json, plus every relative src="…"/href="…" value parsed from the HTML with the regex /(?:src|href)=["']([^"']+)["']/g (absolute URLs, protocol-relative and # links are skipped). All gathered URLs are added to the cache.
  2. activateDeletes every cache key that is not CACHE_NAME — this is how migration between shell versions happens — and then clients.claim() so the new worker controls existing tabs without waiting for a reload.
  3. fetch (GET only)Non-GET requests are never intercepted. Dev resources (/src/ paths, .tsx, .ts, .css) bypass straight to the network so a stale cache can never serve old modules.
  4. Navigations → Network FirstWhen request.mode === 'navigate', destination === 'document', the path is /, or it ends in .html: try the network first, update the cache in the background on a 200 response, and fall back to the cached copy (or cached index.html) only when the network fails. This keeps the shell fresh while remaining offline-tolerant.
  5. Hashed/static assets → Cache FirstEverything else: serve from the cache when present; otherwise fetch, cache the 200, and return. Covered assets are content-hashed by Vite, so a cached file is correct by construction.
SHELL vs ASSETS — THE CORE MENTAL MODEL

HTML is fetched fresh and cached as fallback; JS/CSS chunks are trusted from the cache because their filenames change when content changes. The exception is public/ itself — those files keep stable names, so the only way a new manifest or favicon reaches installed clients is the shell being re-fetched and CACHE_NAME having been bumped by you.

Registration rules

The inline script in index.html gates registration:

const isLocalDev = window.location.hostname === 'localhost' ||
  window.location.hostname === '127.0.0.1' ||
  window.location.hostname === '::1';
  • On localhost / 127.0.0.1 / ::1: any existing service worker registrations are unregistered and every webxreader-* cache is deleted. Dev-mode hygiene: a leftover production cache from a previous deploy must never shadow a dev server.
  • On http(s) but not those hosts: navigator.serviceWorker.register('./sw.js') on window load, followed by an immediate reg.update().
  • file:// or other non-http schemes: never registered at all.

Shell discovery, verbatim excerpts

The asset discovery seeded at install — note how little it trusts: only the app's own index.html and what it references relatively:

async function discoverShellAssets() {
  const indexUrl = appUrl('index.html');
  const response = await fetch(indexUrl, { cache: 'no-cache' });
  if (!response.ok) throw new Error(`Could not fetch application shell (${response.status})`);

  const html = await response.text();
  const assets = new Set([
    indexUrl,
    appUrl('favicon.ico'),
    appUrl('webxreader.svg'),
    appUrl('manifest.json'),
  ]);
  const assetPattern = /(?:src|href)=["']([^"']+)["']/g;
  let match;
  while ((match = assetPattern.exec(html)) !== null) {
    const value = match[1];
    if (!value || value.startsWith('http') || value.startsWith('//') || value.startsWith('#')) continue;
    assets.add(new URL(value, indexUrl).toString());
  }
  return [...assets];
}

Migration on activate is one guard clause — this whole block is what a CACHE_NAME bump actually triggers:

self.addEventListener('activate', (event) => {
  event.waitUntil(
    caches.keys().then((keys) => {
      return Promise.all(
        keys.map((key) => {
          if (key !== CACHE_NAME) {
            console.log('[SW] Removing old cache:', key);
            return caches.delete(key);
          }
        })
      );
    }).then(() => self.clients.claim())
  );
});

INSTALL PROMPT CAVEATS

Installability depends on the host serving https (or localhost) and the SW registering successfully — and some browsers additionally gate the install prompt on icon sizes. Since WebXReader currently declares only the favicon.ico icon, Chrome-style installability generally works, but larger maskable PNG icons in the manifest would strengthen install UX on Android. Advice: if you extend icons, also update discoverShellAssets in sw.js and bump CACHE_NAME so seeded assets match.

Firebase configuration

Two config files drive deploys:

.firebaserc:
{
  "projects": { "default": "xensenx" },
  "targets": { "xensenx": { "hosting": { "webxreader": [ "webxreader" ] } } }
}

firebase.json:
{
  "hosting": {
    "target": "webxreader",
    "public": "dist",
    "ignore": [ "firebase.json", "**/.*", "**/node_modules/**" ]
  }
}

Notes:

  • The hosting target webxreader maps to the site named webxreader, which is why the public URL is https://webxreader.web.app/.
  • public: "dist" — deploys push the built bundle, never src/.
  • No "rewrites" exist and none are needed (hash routing). The ignore array only saves the CLI from uploading metadata files.

CI/CD: the Firebase workflow

.github/workflows/firebase-hosting-production.yml deploys on every push to main. Nothing else — no PR preview deploys, no scheduled builds. End to end:

  1. Triggeron: push → main only. Concurrency group firebase-hosting-production with cancel-in-progress: true, so a rapid second push kills the first deploy rather than queueing both.
  2. Permissionscontents: read plus id-token: write — the latter mints OIDC tokens for the federation step. No secret values are stored in the repo at all.
  3. EnvironmentUbuntu runner, Node 22 via actions/setup-node@v4 with npm caching.
  4. Buildnpm ci then npm run build — which is tsc -b && vite build, so a type error fails the workflow before any deploy.
  5. CLInpm install --global firebase-tools.
  6. Authenticate via Workload Identity Federationgoogle-github-actions/auth@v3 with project_id: xensenx, provider projects/1000429566837/locations/global/workloadIdentityPools/github-actions/providers/github, and service account firebase-hosting-deployer@xensenx.iam.gserviceaccount.com. This exchanges the runner's OIDC token directly for short-lived Google credentials.
  7. Deployfirebase deploy --only hosting:webxreader --project xensenx --non-interactive publishes the new dist/.
WORKLOAD IDENTITY FEDERATION MEANS NO SECRETS

Classic Firebase deploy workflows keep a long-lived FIREBASE_TOKEN secret. This one instead trusts the GitHub OIDC provider configured in the Google Cloud project (github-actions workload identity pool, github provider). Rotating nothing and having nothing to leak is the win; the tradeoff is that IAM changes live in the Google Cloud project, not in GitHub.

THE WORKFLOW DOES NOT RUN TESTS

Only tsc type-checking stands between you and production. There is currently no CI test job — see Testing & Quality → known gaps for the recommended addition (a test step in this workflow or a separate workflow).

Running your own mirror

The three existing mirrors are all connected to the same repository/distro and configured with a single knob each. Replicating one is mechanical:

  1. Cloudflare PagesCreate a Pages project (name it webxreader to reuse webxreader.pages.dev), point it at this repo, set the build command to npm run build and the output directory to dist. No framework preset, no rewrite rules needed.
  2. Vercel / NetlifySame two fields (build command, dist output). Leave rewrites/redirects empty — SPA rewrites are actively unnecessary here, and a catch-all-to-index.html rewrite is harmless but pointless with hash routing.
  3. Update about page + docsAny new mirror URL must be added to the mirrors array in src/components/settings/InformationPage.tsx so the in-app About page keeps its promise of listing mirrors.
SANITY-CHECK A MIRROR LIKE THE MAIN SITE

Each mirror serves the same dist/, so the same offline/install checks from the ops checklist apply. If a mirror starts behaving differently (e.g. an old shell), compare its served index.html asset hashes against the primary — the difference is at the host layer, never in dist/.

ADVICE: TEST THE WORKER ON A REAL HTTPS HOST

Because the SW refuses to activate on localhost (by design), the only ways to exercise it are npm run preview for bundle-level checks plus an https deploy — do the offline/ install verification on the Firebase (or any mirror) deployment. For a faster loop you can run Vite with --host on a LAN https address; the hostname gate only excludes localhost, 127.0.0.1 and ::1.

Cache & versioning cheat-sheet

You changed…What updates itAction needed
App source (src/)Vite emits new content-hashed chunks; HTML references changeNothing manual — Network-First shell + hashed assets self-propagate
public/ files (sw.js, manifest.json, favicon.ico, webxreader.svg)The SW caches them by CACHE_NAMEBump CACHE_NAME (e.g. webxreader-shell-v6) whenever a public asset's content changes
index.htmlNetwork-First navigationNothing manual; browsers may still cache HTML briefly — hard refresh verifies
IndexedDB schema / backup formatRuntime migration code in core/storageNot a cache concern — export a backup first (below)
Behind-the-file URLs (e.g. docs, mirrors)Host-level cachingInvalidate per host (Firebase/Cloudflare/Vercel/Netlify consoles) if needed

Why the manual bump matters: public/ files keep stable names, so a client's Cache-First rule would happily serve last year's manifest forever. The activate handler deletes caches whose name differs from CACHE_NAME — bumping the name is what triggers that deletion wave for existing installs (they re-download everything on next activation).

Ops checklist

  1. Export a backup before schema-affecting deploysUse the in-app backup export (Import & Backup) before deploying changes to stores or migration logic. clearDatabase() exists for tests, not as a mitigation for app data.
  2. Verify the SW version after deploying asset-level changesDevTools → Application → Service Workers: the active worker should be webxreader-shell-v5 (or whatever you bumped to), and Cache Storage should contain exactly one webxreader-shell-* cache.
  3. Check offliningWith DevTools offline (or the airplane toggle), reload: the shell, chunks and previously opened books should still come up. A blank screen here usually means the bump/activate cycle was skipped.
  4. Confirm all four mirrors after a big deployPrimary and mirrors deploy independently; a broken mirror is a config problem on that host, not in dist/.
  5. Test import → read → progress on the deployed buildjsdom tests cannot cover canvas/iframe rendering paths; a quick real-file run on https builds is the only real smoke test available (Testing & Quality).

These docs could be hosted from /docs

This documentation site is plain HTML + docs/assets/style.css + docs/assets/script.js with no build step: no Eleventy, no Quarto, no templating. That makes it deployable as-is from the /docs folder of any branch via GitHub Pages (settings → Pages → "Deploy from branch"), which the repo accommodates with a .nojekyll marker file. Pages reference each other with root-relative paths (index.html, reader.html, …), so publishing the folder verbatim — as GitHub Pages does automatically — just works. If you move the docs site onto its own branch or repo, keep the flat file layout and relative links intact.
