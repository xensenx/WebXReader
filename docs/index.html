The three design pillars

Everything in the codebase follows from three commitments. Understanding them makes most architectural decisions obvious:

1. Local-first by default

  • All reader data is client-side. Books, extracted chapters, covers, reading progress, bookmarks, annotations, per-book settings — stored in IndexedDB under the database webxreader.
  • Site preferences (theme, library layout, sort order, import thresholds) live in localStorage under the key webxreader.preferences.v1, with a one-time migration path reading from legacy IndexedDB.
  • Original files are preserved for EPUB, PDF and CBZ: the raw ArrayBuffer of what you imported, so you can re-open the book byte-for-byte and re-download it from the details dialog.
  • Data is portable — a JSON backup format (version 1 and 2) covers everything including the original binary files, generated fully client-side (see Import & Backup).
WHAT "local-first" MEANS HERE

There is no backend. Firebase is used only to host the static build (see PWA & Deployment). A request in flight typically means fetching app assets from the CDN or a cover image URL, nothing more.

2. Privacy by construction

  • Reader-facing HTML (EPUB chapters, TXT/MD/HTML chapters restored from backups) is sanitized with DOMPurify before render (src/core/parsing/sanitize-reader-html.ts).
  • Imported HTML is also pre-escaped/scrubbed by sanitizeHtml() in src/utils/index.ts (strips <script>, on* handlers, javascript: URLs).
  • Markdown rendering uses marked + DOMPurify, never raw injection.
  • No analytics, no telemetry, no remote logging anywhere in src/.

3. Each format is a world of its own

Reflowable prose (TXT/MD/HTML) and fixed-layout media (PDF pages, comic panels) share a shell (ReaderView, drawers, progress bar, zoom) but delegate actual rendering to per-format engines laid out under src/formats/engines/. What a given format supports — search, zoom, reading direction, typography — is declared in a central capability matrix, not scattered through conditional UI code. The Formats & Parsers chapter documents the registry; the Reader chapter documents how engines consume it.

Where to go from here

The documentation is split into twelve chapters, ordered roughly the way the app is layered.

Introduction

  • Getting Started — Node and npm versions, dev server, build, test, lint commands, plus what not to configure (there are no .env files).

Core chapters

  • Architecture — stack, folder map, routing, providers vs hooks, lazy loading and chunking, CSS design tokens.
  • Data Model — every type exported from src/types/book.ts, including exact defaults of DEFAULT_SETTINGS.
  • Formats & Parsers — registry API, capability matrix, per-format parse pipeline, parsers, sanitization, natural sorting for CBZ pages.
  • Reader Engine — ReaderView, the five engines, zoom mechanics, progress and resume semantics per format, keyboard shortcuts.
  • Library & Metadata — grid/list layouts, filters, sorting, custom drag order, book details dialog, cover editor, import dialog.
  • Storage & Persistence — full IndexedDB schema (8 stores, all indexes), database API, settings stores and migration.
  • Import & Backup — the nine-step import pipeline, dedup, backup v1/v2, restore-time validation and sanitization.

Development & operations

  • Testing & Quality — the Vitest harness, each of the 12 suites, fixtures, test-time mocks, oxlint.
  • PWA & Deployment — service-worker strategy, manifest, Firebase Hosting CI with Workload Identity Federation, mirror URLs.
  • Roadmap & Known Gaps — planned features (statistics dashboard, dictionary, ambient audio…), deliberately excluded items (like TTS), future formats, and open audit items to consider as a contributor.

How to read these docs

  • Everything described on these pages is verified against the code on the Exp/set-1 branch; file paths are repo-relative from the project root.
  • Where a specific value matters (a cache name, DB version, default font size, debounce delay) it is quoted verbatim, so it is safe to bet implementation code against these tables.
  • Sections marked Known gap highlight an inconsistency found while writing these docs — they are worth reading before refactoring those areas.
  • Use / or the search box above to find any concept across all chapters; results link straight to the matching section anchor.
